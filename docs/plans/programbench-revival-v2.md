## §1 — Objective (outcome-shape, one sentence)

Produce a **definite, independently-judged, evidence-backed verdict** on whether the real sealed v0.11.0 hands-off loop (the loam arm) materially outperforms a bare `claude -p` baseline (the no-harness arm) at executing a frozen set of **non-subjective ProgramBench-class hands-off tasks** stated as a non-technical user would state them — where "materially outperforms" is decided by a pre-declared margin on a scoring authority that is the **independent held-out judge, never the loop's own AC.B.4b judge**, and where **"loam does not materially beat the baseline" is a first-class plan-success outcome reported straight, never retried to green.**

This ladders to **both** VALUE_PROPOSITION tests jointly: if the harness does not measurably reduce the non-tech-user intent→AI-effective-execution gap relative to raw Claude on tasks raw Claude can be given directly, the harness's reason to exist is unproven; v2 is the prime-objective-level measurement of exactly that claim.

## §5 — Acceptance criteria (`AC.PBR.*`, outcome-shape, method-in-AC test passed per-AC)

The method-in-AC test applied to each: *can this AC be satisfied by a method other than the one I have in mind? Yes ⇒ tight scope (good). No ⇒ method stated (Lens-3 violation).* Each AC carries its satisfiability note. The honest-negative ("loam does not materially beat the baseline") is a **first-class valid polarity** on the lead AC (AC.PBR.7) by construction — there is no green-only success path.

### AC.PBR.1 — Two arms are defined, isolated, and identically tasked

There exist exactly two arms run on the **same** frozen task set with the **same** model tier (default Sonnet per token-efficiency; no `model-rationale` needed), the **same** single plain-language task statement per task, and the **same closed (no-answer) user channel** for the duration of every run:
- **Baseline arm (no-harness floor):** a single bare `claude -p` invocation given the task's plain-language statement and nothing else (no decompose, no independent verify, no refinement, no persistence) — raw model capability, the documented floor.
- **Loam arm:** the real sealed v0.11.0 hands-off loop driven through its actual persona-invocable entry surface (`handsoff-loop run`), no mock, no pre-loop machinery.

**Zero-interaction parity (binding — ProgramBench is one-shot; owner constraint Telegram 11443).** Every (arm, task) run produces its output **solely from the single task prompt**, with **zero interactive back-and-forth for either arm**. No system — neither arm — is granted a simulated, scripted, or stand-in user that answers questions or approves a gate during the run. Where an arm's machinery would, in normal interactive operation, refine intake / ask a clarifying question / wait at an approval gate, running it under the closed channel degrades to exactly two permitted outcomes: (i) **internal best-effort inference** from the single prompt and proceed; or (ii) where the arm genuinely cannot resolve the task without an answer, an **honest negative / honest-refuse on that task** — which the independent judge scores as a **non-pass** (AC.PBR.3/.4), never simulated to success, never hung waiting, never retried for an answer. The two arms therefore receive **identical input** (the single prompt + a closed channel); the only difference under measurement is the loop's **internal** machinery (decompose → dispatch → independent-verify → refine-internally → persist) operating from that same single prompt — not any interaction the loop gets and the baseline does not.

Each arm's per-task run is environment-isolated from every other run (no residual state carried between tasks or arms) and isolated from the task's ground-truth check (the agent in either arm never sees the scoring command).

- *Ladders to:* both tests (the comparison only measures harness-attributable value if the only difference between arms is the harness's internal machinery operating on identical zero-interaction input).
- *Satisfiability:* satisfiable by per-task subprocess isolation, by per-task fresh work-dirs, by container-shaped isolation; the closed-channel constraint is satisfiable by an empty/declining intake-answer source, by driving the loop with `--frozen`/`--from-intake` so no live question is ever posed, by a non-answering channel stub that the judge scores any unmet question against — multiple methods; the AC constrains *same-task / same-model / single-prompt / closed-channel-both-arms / arm-isolated / ground-truth-isolated / unresolvable-without-answer ⇒ scored non-pass*, not the isolation mechanism and not how non-interactivity is realised. Tight (each clause satisfiable more than one way).
- *External corroboration:* this is ABC "task validity" (environment isolation + agent-isolated-from-ground-truth) — adopted as framing because it IS loam's own sealed freeze-isolation spine (`FrozenAcceptance.assert_unseen_by`), externally confirmed, not a new method. The zero-interaction clause is additionally corroborated by the Anthropic agent-evals guidance that an unclear task spec is an *eval-design* failure and a well-specified task should reach the same verdict from two independent experts *without* a clarifying round (web falsify/improve pass, §6) — so a non-subjective PB task being answerable from the single prompt is the expected case, not an artificial handicap; the τ-bench-style "simulate the user with a second LLM" pattern from that same guidance is explicitly **NOT adopted** (it is the conversational-benchmark pattern 11443 rules out for a one-shot benchmark — Lens 1: do not copy the popular design uncritically).

### AC.PBR.2 — The task set is the frozen non-subjective ProgramBench set, content-pinned and sized for a definite verdict

The experiment runs against a **named, content-hash-pinned** set of non-subjective ProgramBench-class tasks. Each task carries: a plain-language non-technical-user statement of intent + a **positive real-outcome floor check** + a held-out anti-overfit check absent from every prompt.

**Positive real-outcome floor check (the failure-boundary-as-positive-objective binding).** Every task's deterministic machine check is authored as a **positive assertion of the real outcome**: it exits 0 **iff the real outcome was actually delivered into the world the task names**, and a **nominal-but-hollow result is a non-pass by construction** — specifically, a result that compiled / ran / returned a friendly summary but produced **no real effect** (compiled-but-no-effect), an **empty / vacuous extraction**, or **left the named target untouched** must drive the check to a non-zero exit, *not* a pass. The floor is a positive objective ("the real outcome IS present"), never a negative side-condition bolted on after a surface check. **Worked illustration (the owner's email task, Telegram 11447):** a task of the shape "address a real issue with the user's email" passes only if the check can positively assert that the user's email was **actually changed in the way the issue required** (the real mailbox / config / rule state now differs in the asserted direction); an arm that **did not touch the email**, performed a no-op, or returned a plausible report without effecting the change is a **total failure on that task even if some minor one-time action would have sufficed** — "I would have / it looks done" is not the real outcome. The set is sized so the aggregate verdict is **definite** (every task gets a definite per-task disposition; no task left indeterminate by under-powering) while honouring the cost ceiling (D-PBR-4). The genuinely-subjective objective class is **excluded by construction** (§7), not worked around.

- *Ladders to:* harness test (the toolkit claim is only measurable on tasks whose real outcome — not a surface proxy — is machine-checkable) + primary-persona test (tasks stated as a non-tech user states them; the floor is exactly the non-tech user's "did it actually fix my thing").
- *Satisfiability:* satisfiable by the public ProgramBench non-subjective subset, by a hand-curated ProgramBench-shape set (v0.4.0 C4 precedent shows real-leaderboard eval may be host-blocked — a documented signal-bearing substitute at honest scope is acceptable IF it carries the same positive-real-outcome-floor property), by a mix — multiple methods; and the floor itself is satisfiable by more than one authoring method (a post-state assertion against the named real target, a side-effect-presence assertion, a before/after state-diff that must show the asserted change) — the AC constrains *non-subjective + content-pinned + positive-real-outcome-floor-per-task (hollow ⇒ non-pass by construction) + sized-for-definite*, not the sourcing and not how each floor check is authored. Tight (the per-task floor-check authoring stays the builder's method). **Builder halt-trigger:** if the real public set is host-blocked (the C4 Docker/linux-amd64 block), the builder ships a documented honest-scope substitute that preserves the positive-real-outcome-floor property and says so plainly in the report — it does NOT silently shrink scope or fake real-leaderboard numbers (§8.2).
- *External corroboration:* this IS ABC outcome-validity hardened to the false-success class — externally corroborated by the evidence-supported-bounds discipline (pre-run specification of *which artefact would prove the intended state change occurred*, scored post-run so a surface signal like "clicked Save" is not counted as the outcome) and the corrupt-success literature (a nominal terminal-state success that did not effect the real change is flagged, not passed). Adopted **as framing**; loam's deterministic-machine-check-exits-0-iff-real-outcome + held-out anti-overfit + tool-grounded adversarial independent judge (AC.PBR.3/.4) is **kept as the implementation** — it is already the stronger shape for this exact failure mode. No external method adopted wholesale (the corrupt-success six-dimensional procedural gate is a conversational-policy construct, not applicable to a one-shot non-subjective deterministic-outcome benchmark — §6 per-part decision).

### AC.PBR.3 — The scoring authority is the independent held-out judge, never the loop's own judge

Every per-task disposition (for BOTH arms) is decided by the **independent, adversarial, tool-grounded held-out judge** (the proven `_independent_judge` methodology: a separate, stricter, differently-framed `claude` probe forced to enumerate what a literal exit-0 of the raw machine check would and would NOT guarantee, spawned through the sealed `spawn_isolated_claude` surface) — and **provably NOT** the loop's own `intake.py` AC.B.4b faithfulness judge. The judge classifies each arm-task into a definite tag (faithful / checkable-but-wrong / honest-negative / indeterminate) grounded in the check command, not the friendly summary.

- *Ladders to:* both tests (a measurement scored by the thing being measured is not a measurement — §3.2 evidence: the loop's own judge scored I5/I6 `faithful=True` while the independent judge correctly scored them `CHECKABLE-BUT-WRONG`).
- *Satisfiability:* satisfiable by reusing the sealed `_independent_judge`, by an equivalently-held-out differently-framed adversarial judge process, by a deterministic check + held-out judge ensemble — multiple methods; the AC constrains *independent + held-out + tool-grounded + provably-not-the-loop-judge*, not the judge's prompt wording. Tight.
- *External corroboration:* this IS ABC "outcome validity" (the check must indicate task-solved, not a proxy). Adopted as framing; the loam methodology is *stronger* than ABC's generic LLM-judge recommendation because it is tool-executing + held-out + adversarial. No external method adopted wholesale — ours is kept because it is already the better-reviewed shape for this exact failure mode.

### AC.PBR.4 — A run is declared pass/fail per task on a pre-frozen rule, no retry-to-pass

For each (arm, task), the pass/fail disposition is computed by a **rule frozen before any run** (content-hash-pinned alongside the task set): a task is "passed" for an arm iff the independent judge tags it faithful AND the **positive real-outcome floor check** (AC.PBR.2 — exits 0 iff the real outcome was actually delivered; a compiled-but-no-effect / empty-extraction / target-untouched result is a non-pass by construction) exits 0 AND the held-out anti-overfit check exits 0 (the proven both-must-pass spine, `verify.py:213-215`). Each (arm, task) is run **once, no retry-to-pass** for the headline number; a bounded small-k re-run (D-PBR-3) runs ONLY on the tasks at the decision margin, for consistency reporting, never to flip a fail to a pass.

- *Ladders to:* harness test (a movable pass bar measures nothing).
- *Satisfiability:* satisfiable by an exit-code-AND-judge-tag conjunction, by a frozen rubric scorer, by a deterministic gate + judge gate — multiple methods; the AC constrains *pre-frozen rule + both-checks + no-retry-to-pass*, not the scoring expression. Tight.
- *External corroboration:* ABC "contamination prevention / no test-signal-driven agent modification" — adopted as the no-retry-to-pass + frozen-before-run constraint (this is also loam's own freeze-before-any-sub-agent spine).

### AC.PBR.5 — The "materially beats" margin is pre-declared and the answer is a number, not a vibe

The experiment carries a **pre-declared decision rule** (frozen before any run, in the plan or a content-pinned config) that maps the two arms' independently-judged pass profiles to one of exactly three definite verdicts. The margin is **FROZEN-RATIFIED (D-PBR-1, owner Telegram 11447 — no longer owner-ratification-pending; the builder freezes exactly this and does NOT move it after runs begin)**:

- **(a) loam materially beats baseline** — BOTH of the following hold on the independently-judged dispositions: (i) among the tasks for which the **baseline arm** is independently judged a **non-pass**, the **loam arm** is independently judged a **pass** on a **clear majority** of them; AND (ii) loam's **total** independently-judged pass count does **not regress below** the baseline's total independently-judged pass count.
- **(b) loam does not materially beat baseline** — the margin in (a) is not cleared (either the clear-majority-of-baseline-misses condition fails, or loam's total pass count regresses below baseline's). A **first-class plan-success outcome**, reported straight.
- **(c) indeterminate** — the task set could not produce a definite picture (e.g. too few baseline non-passes to define a clear majority, or under-powered) — itself a definite, reportable finding that names why.

The verdict is computed from the numbers, not asserted. **"Every task is independently judged a pass" (the owner's all-tasks-complete hope) is recorded as a DOCUMENTED ASPIRATIONAL / secondary reported metric in AC.PBR.7 — it is explicitly NOT the v2 pass/fail gate; the gate is the (a)/(b)/(c) rule above.**

- *Ladders to:* both tests jointly — this is the AC that turns the prime-objective question into a decidable number.
- *Satisfiability:* the FROZEN margin shape (clear-majority-of-baseline-misses-recovered AND no-total-regression) is itself satisfiable by more than one numeric expression of "clear majority" (a strict >50% count, a pre-pinned fraction threshold, a paired sign-test on the baseline-miss subset) and "no regression" (≥ on raw counts, ≥ on honest-coverage fraction) — the AC constrains *pre-declared + three-valued + computed-not-asserted + honest-negative-first-class + the two frozen conditions*, not which numeric form of "clear majority" / "no regression" the builder pins at freeze time. **Bar-fairness note (F2):** the margin is a *fair honest test* by construction — recovering a clear majority of the baseline's own misses (not a trivially-clearable absolute count) while forbidding any total-pass regression cannot be cleared by a loam arm that merely matches the floor, nor does it read a real recovery as a loss. The all-tasks-pass aspirational metric is reported alongside but never substituted for this gate (it would inflate a real partial win into a reported loss).

### AC.PBR.6 — Cost, latency, per-task evidence, and a per-non-pass failure class are captured and reproducible

For every (arm, task) the run records: measured cost (from `--output-format json`'s `total_cost_usd`, never estimated — the proven D-COST-BAND discipline), wall-clock, the raw transcript, the derived/used check command, and the independent judge's verdict + reason. The headline number is reproducible from the preserved evidence (re-running the frozen scorer over the preserved per-task artefacts yields the same verdict).

**Per-(arm,task) failure-class tagging (the false-success-class binding).** Every (arm, task) judged a **non-pass** additionally carries a **failure class drawn from a small fixed taxonomy frozen with the task set**, at minimum: **did-not-produce-output** (no artefact / no result at all), **produced-but-no-real-effect** (the nominal-but-hollow / compiled-but-no-effect / empty-extraction / target-untouched class — the false-success class AC.PBR.2's floor is built to catch), **produced-but-wrong** (a real effect was delivered but it is the wrong outcome), and **honest-negative-refusal** (the arm honestly declined / surfaced it could not resolve the task — a first-class disposition, never retried-to-green per AC.PBR.7). Every recorded non-pass maps to exactly one class so the verdict is a **failure-signature map per arm, not only a pass count** — this is what makes the result able to answer *"how well does each arm do specifically against the false-success class"* (the owner's Telegram 11447 concern: compiled-but-no-result / empty extraction / didn't-touch-the-target nominally reported as done). The taxonomy is the **outcome**; how each non-pass is classified into it (judge-tag mapping, a deterministic-check-signature rule, an explicit classifier probe) is the **builder's call**.

- *Ladders to:* harness test (a number nobody can reproduce or cost-account is not a harness measurement, and a pass-count with no failure-signature cannot answer the false-success question VALUE_PROPOSITION's translation-burden test turns on; VALUE_PROPOSITION names token/cost discipline as the harness's own obligation).
- *Satisfiability:* satisfiable by a per-run JSON evidence record, by a structured run-log, by the `.phase_verdicts/`-shaped artefact dir — multiple methods; the failure-class itself is satisfiable by mapping the independent judge's existing tags onto the four classes, by a deterministic check-exit-signature rule, by a dedicated classifier probe — multiple methods; the AC constrains *measured-cost + latency + raw-evidence + reproducible-headline + every-non-pass-carries-exactly-one-failure-class-from-the-frozen-taxonomy*, not the record format and not the classification mechanism. Tight.
- *External corroboration:* ABC "benchmark reporting" (cost/latency + transparent reproducible reporting) — **PARTIAL adopt** (see §6 per-part decision): cost/latency + reproducibility ADOPTED; full statistical pass@k across all tasks NOT adopted (cost discipline + the architectural-verdict shape of the question per `feedback_n1_architectural_vs_n3_statistical` — small-k only at the margin, D-PBR-3). The per-non-pass failure-class is corroborated by the evidence-supported-bounds discipline (a non-passing run carries a *reason class*, not only a polarity — pass / fail / undecided with a per-record blocking-reason class) — **PARTIAL adopt as framing**: the requirement that a non-pass carry a reason class is adopted; the experiment's small fixed four-class false-success-oriented taxonomy is **kept as the outcome** because it is the taxonomy that answers *this* experiment's false-success question (the external per-model-signature taxonomies are model-diagnostic, not the false-success map this verdict needs). No external taxonomy adopted wholesale (§6 per-part decision).

### AC.PBR.7 — The verdict report answers the prime-objective question (lead AC; honest-negative valid)

A report at `docs/experiments/programbench-revival-v2.md` carries: the two arms' definite per-task disposition tables, the independently-judged honest-coverage of each arm, the **per-arm failure-signature map** (the AC.PBR.6 fixed-taxonomy non-pass class counts — so a reader sees not just how many each arm missed but *how* it missed, with the false-success "produced-but-no-real-effect" class explicit per arm), the **FROZEN-RATIFIED margin (D-PBR-1: clear majority of the baseline's independently-judged misses recovered by loam AND no regression in loam's total pass count)**, the computed three-valued verdict, the **all-tasks-pass aspirational/secondary metric reported alongside but explicitly labelled NOT the gate**, the measured cost/latency per arm, and a plain-language answer a non-technical reader can act on to the exact question **"does loam materially beat a bare LLM at hands-off task execution for a non-technical user, and by how much, judged by something other than loam's own judge?"** — **OR** a definite, evidence-backed honest-negative / indeterminate that names *why* the comparison could not return a material-win verdict.

- *Ladders to:* both VALUE_PROPOSITION tests jointly — the prime-objective-level deliverable.
- *Satisfiability:* the AC is "a definite, independently-judged, evidence-backed three-valued verdict + plain answer exists" — satisfiable by *any* polarity (material win, no-material-win, indeterminate) and any independent dimension-grounded judging method. Not green-only, not method-bound. **A "loam does not materially beat the baseline on this set — here is the evidence" finding satisfies this AC exactly as a material-win finding does, is reported straight, and is NEVER retried to green, NEVER the margin weakened, NEVER widened into re-running until loam wins** (F2 / locked-design-not-license).

## §10 — F2 Ruthless Feedback (honest doubts, named with evidence + alternative)

1. **n=1-per-task is a deliberate architectural-verdict choice, not under-powering — but it is a real limitation and is named, not papered.** Evidence: `feedback_n1_architectural_vs_n3_statistical` (architectural question + prior-informed hypothesis + large-effect + binary verifier + meaningful cost-per-rep ⇒ n=1 sufficient on the load-bearing case). Alternative considered + rejected: full statistical pass@k across all tasks — rejected because it burns the cost ceiling and the question ("does the harness beat the floor *at all*") is architectural, not "by exactly how many percent with a CI". Mitigation kept: small-k re-run at the decision margin only (D-PBR-3) for consistency reporting. The report MUST state the n=1-per-task limitation in plain language — a reader must not over-read a single-run delta as a stable population estimate.
2. **The loam arm's intake/approval gate runs under a CLOSED user channel — no simulated user, by binding constraint.** ProgramBench is one-shot: every system produces its output solely from the single task prompt with zero interactive back-and-forth (owner constraint Telegram 11443; bound as AC.PBR.1 zero-interaction parity + recorded §3.5 + D-PBR-6). The earlier-considered cooperative-user simulation (`_cooperative_user` / `_agrees_to_milestone`, `handsoff_loop_goal_refine_reharden.py:146-166`) was a defensible modelling choice **before 11443 was explicit** and is now **removed as the loam-arm model**: it would grant the loam arm a simulated interaction PB grants no system, so the loam arm would not produce output solely from the single prompt and the two arms would not receive identical input (locked-design-not-license — a plan written before the constraint is revisable). It is **NOT** "the harness value under test." What IS under test: whether the loop's **internal** machinery (decompose → dispatch → independent-verify → refine-internally → persist) produces a better independently-judged outcome from the **same single prompt** than bare `claude -p` given that same prompt — input parity is total; the only delta is internal machinery. Evidence the verdict logic does NOT structurally depend on simulated interaction: the loam arm drives `handsoff-loop run --frozen`/`--from-intake` and the loop decides done by *executing the frozen check* (`verify.py:170-224`), independently judged (AC.PBR.3) — the cooperative-user shape only ever fed the *intake-refinement leg*, not the verify/judge spine, so removing it is a localized correction, not a verdict-logic rewrite. Residual honest limitation the report MUST name (this is a real limitation, named not papered): a task that genuinely cannot be resolved without an answer is, under the closed channel, an honest-negative non-pass for the loam arm (and a corresponding non-pass for the baseline arm, which also has no channel) — that is the correct, in-intent disposition for a one-shot benchmark, not a confound to engineer away and not a reason to re-pick tasks. Alternative considered + rejected: a real or simulated human gate per task — rejected as out of ProgramBench intent per 11443, not merely "not scalable."
3. **"Materially beats" was a critical-call owner gate — now FROZEN-RATIFIED (D-PBR-1, owner Telegram 11447), no longer pending.** The margin determines what counts as the harness proving its reason to exist; per `feedback_test_against_operational_objective_before_escalating` the operational objective did NOT imply a single obvious margin number, so it was surfaced for owner ratification rather than decided autonomously. The owner ratified the goal "beat raw Claude" and the margin shape is now frozen in AC.PBR.5 (clear majority of the baseline's own independently-judged misses recovered by loam AND no regression in loam's total independently-judged pass count). The builder freezes exactly this and does NOT move it after runs begin. The owner's "every task complete" hope is captured as a documented aspirational/secondary metric in AC.PBR.7, explicitly NOT the gate (per the same Telegram 11447 directive). No remaining owner gate inside this plan — everything else is recommendation-default.
4. **The prior ProgramBench history is a trap the report must not fall into.** v0.4.0/v0.4.1/v0.4.2 reported "100% (16/16) STRICT" — on 3 toy tasks, against the code-gen surface, NOT the loop, NOT independently judged. Evidence: `docs/release-roadmap.md:58-60`. Alternative to avoid: reusing those toy tasks or that framing. The v2 report MUST explicitly state it is a different, harder, independently-judged measurement and MUST NOT inherit the toy-task pass-rate framing — conflating them would be the exact dishonesty `feedback_no_count_padding` + claim-or-cite guard against.
5. **Risk most likely to retire negative (named up front, expected-possible, the plan working):** the loop may NOT materially beat the bare baseline on non-subjective program-synthesis tasks specifically — bare `claude -p` is already strong at well-specified single-shot coding (the C4 baseline scored 100% on toy tasks *without* the harness). The harness's distinctive value is translation-burden absorption on *under-specified* intent, not raw coding capability. If the non-subjective set is well-specified enough that bare Claude already nails it, loam may not show a material delta — and **that is a true, valuable, plan-success finding** (it would say: the harness's value is in the under-specified/subjective regime, which is exactly the regime owner-ruled out of scope for v2). The report must frame a no-material-win as this specific, informative result — NOT as a loam failure and NOT as a reason to re-pick easier tasks.
