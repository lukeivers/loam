## §1 Summary / TL;DR

**What ships (increment 3 only):** **INTAKE** — loam detecting a piece of work the user mentions in an ordinary conversational turn (a task, a follow-up, a thing to do, a blocker) and turning it into a work item in the increment-2 store, at a **LIGHT default**: detect-and-PROPOSE (surface one plain-language "want me to track this?"), never silently auto-create a pile, never nag. The proposal is a real work item created in the store's `proposed` lifecycle state; a plain-language confirm promotes it to `active`, a dismiss abandons it. Intake **composes on** the #56 intent-extraction seam (the LLM read of the turn) and the #34 interaction-model (the per-user aggressiveness dial), and registers as a keep-pace `TriggerKind.turn` contributor (the same seat the increment-2 lenses use). **It is an EXTENSION of the keep-pace/intake surface, NOT a new component** (§3 D-INTK.1).

**AC families:**
- `AC.INTK.DETECT.*` — a turn carrying work-intent is recognised as work-intent; a turn carrying none is NOT (the no-over-capture discrimination); detection reads the #56 extractor, fail-soft when it declines.
- `AC.INTK.PROPOSE.*` — a detected item is surfaced as ONE plain-language proposal (no ID/enum/path), backed by a real `proposed`-state work item placed with provenance + candidate stream/project; the proposal is NOT a silent commit.
- `AC.INTK.CONFIRM.*` — a plain-language confirm promotes the proposed item to `active`; a plain-language dismiss abandons it; an ignored proposal does not re-nag.
- `AC.INTK.LIGHT.*` — the light default holds: ordinary chatter and one-off "do X once" asks do NOT each become a tracked item; the aggressiveness is read from the #34 `work-tracking` cell, defaulting light.
- `AC.INTK.LIVE.*` — **outcome-altitude**: a real conversational turn mentioning a piece of work, run through the live production turn-path with no pre-arranged state, results in exactly ONE correctly-placed `proposed` work item in the live store at the light default — and a turn of pure chatter results in ZERO.

**Key decisions baked (full list + recommendations in §3):**
1. **EXTEND the keep-pace/intake surface — do NOT build a new component** (§3 D-INTK.1). Intake is a `TriggerKind.turn` keep-pace contributor reading `TurnPayload.prompt`, composing the #56 extractor + the #34 cell; the store is consumed via its existing `create` API. No new store, no new turn-loop.
2. ★ **WMS-D4 — intake aggressiveness default + the auto-create-vs-propose call** (§3 D-INTK.2). RECOMMEND **propose-and-confirm at a LIGHT default**, per-user-tunable via a #34 `work-tracking`/`intake-aggressiveness` cell. **Genuine owner product-shape call** — it sets how often loam interrupts to track work.
3. ★ **Dedup-against-existing-work-items behavior** (§3 D-INTK.3). RECOMMEND **propose-suppress on a near-duplicate** (if the detected item closely matches an open work item already in the store, surface nothing / a one-line "already tracking that" rather than a second proposal). **Genuine owner product-shape call** — it governs whether re-mentions pile up.
4. **Detection composes on the #56 extractor's work-intent read; fail-soft to no-proposal** (§3 D-INTK.4, method-call). When the extractor declines, intake surfaces NO proposal that turn (it does NOT fall back to a regex that over-captures) — silence is the safe default for a quality-LIFT layer.

**F2 RF on scope realism (full treatment in §10):** two load-bearing items. (1) the #56 seam lives in `workspace-bootstrap` and is shaped for the ONBOARDING stop/start question — its `ExtractedIntent` fields (`disposition: stop/start`) are onboarding-specific; work-intake needs a work-shaped read (is-this-work + a title + candidate stream/project), so intake either reuses the `IntentExtractor` Protocol with a work-shaped prompt or adds a sibling extractor — named D-INTK.4 + RF #1. (2) the increment-2 store exists ONLY on `build/wms-increment-2`, NOT `main` — the build MUST stack on that branch; building on `main` would find no `create`-with-`belongs_to_project` surface (RF #2 / halt §8 #1).

## §3 Named decisions (with recommendations) — surface to Luke

Every decision carries a recommendation. ★ flags a genuine **owner product-shape call** (it changes the user's lived experience every turn); the rest are **autonomous method-calls** (the builder takes method from here).

### D-INTK.1 — Extend the keep-pace/intake surface vs a new component. **RECOMMEND: EXTEND `primary-persona` keep-pace (a new `intake.py` contributor) — do NOT build a new component, and do NOT modify the objective-tracker store. Method-call (the architecture + the seams already rule the shape).**
- **Why extend, not new:** intake is a turn-time read (`TurnPayload.prompt`) + a compose of two existing seams (#56 extractor, #34 cell) + a CONSUME of the store's existing `create`/transition API. Every primitive it needs already lives in or beside `primary-persona` keep-pace. A new component would re-create the turn-loop wiring + the contributor registration the keep-pace surface already owns (Lens-1: compose, don't duplicate).
- **Why NOT touch the objective-tracker store:** the increment-2 store ALREADY creates in `proposed`, carries `belongs_to_project`/`tagged_streams`/provenance, and transitions `proposed → active`/`abandoned`. Intake is a pure CONSUMER of that sealed API — this keeps increment 3 single-component (`primary-persona` only) and avoids a second sealed-store amendment. **If intake discovers it needs a store-side change** (e.g. a provenance field the store does not carry), it HALTS rather than silently amending the sealed store (§8 #2).
- **Alternative rejected:** a standalone `work_intake` component. Rejected — duplicates the turn-loop + contributor seam, and splits intake from the lenses it surfaces alongside.

### D-INTK.2 — Intake aggressiveness: the default + auto-create-vs-propose. ★ **RECOMMEND: PROPOSE-and-CONFIRM at a LIGHT default — detect work-intent, surface ONE plain-language "want me to track this?", create the item in `proposed` (not `active`), promote only on confirm. Per-user-tunable via a #34 `work-tracking`/`intake-aggressiveness` cell; the openness default leans LIGHT. This is the one decision that most shapes the user's every-turn experience — worth Luke's deliberate eyeball.**
- **Why propose, not auto-create-active:** the architecture WMS-D4 + §4a name the prime-directive over-reach guard explicitly — "don't turn every 'do X once' into a tracked effort." Silent auto-create-to-active would build the pile of half-real tracked items the whole system exists to avoid, and would violate the single-approval-gate discipline (the verify-before-build step is load-bearing). The `proposed` lifecycle state is EXACTLY the store's seat for "surfaced, not yet committed" — an unconfirmed proposal is a `proposed` item that quietly expires/abandons if never confirmed, so even an ignored proposal leaves no `active` clutter.
- **The aggressiveness levels (the dial #34 reads):** a small ordered set — RECOMMEND three: **`off`** (never propose; user tracks manually), **`light`** (the DEFAULT — propose only on a clear, forward-looking work-intent signal; one proposal, no re-nag), **`eager`** (propose on softer signals; for a power user who WANTS aggressive capture). The default is `light`; the cell is set by demonstrated preference + explicit statement (`apply_override`).
- **The owner call:** confirm **light-default propose-and-confirm** (vs an auto-create default, or a heavier eager default). This is genuinely product-shape: it sets how often loam interrupts the user to ask about tracking work. Recommendation is light propose-and-confirm.

### D-INTK.3 — Dedup against existing work items. ★ **RECOMMEND: PROPOSE-SUPPRESS on a near-duplicate — before surfacing a proposal, check the open work items already in the store; if the detected item closely matches an open one, surface NOTHING (or at most a single quiet "already tracking that"), never a second proposal. Worth Luke's eyeball — it governs whether re-mentioning a thing piles up duplicates.**
- **Why suppress:** the user will mention the same piece of work across many turns ("still need to do the rental paperwork" said three days running). Without dedup, the light default still produces three proposals → three `proposed` items → the exact pile the system avoids. Suppressing on a near-match keeps re-mentions from cluttering.
- **The match shape (method-call within this ★ decision):** a title/intent similarity check against the OPEN items (`proposed`/`active`/`blocked`) — the builder's call whether that is a normalized-string match, an embedding, or a small LLM "is this the same work?" read; the OUTCOME (a re-mention of an already-tracked thing does not create a duplicate) is the AC, not the match method.
- **The honest tension (F2):** an over-aggressive dedup SUPPRESSES a genuinely-new item that merely sounds similar (a false-merge), which is worse than a duplicate (the new work silently vanishes). RECOMMEND biasing dedup CONSERVATIVE — suppress only on a HIGH-confidence match; when unsure, propose (a visible duplicate the user can dismiss beats a silently-dropped new item). The owner call: confirm propose-suppress with a conservative (high-confidence-only) match bias.

### D-INTK.4 — Detection composes on the #56 extractor; the work-shaped read; fail-soft to no-proposal. **RECOMMEND: reuse the #56 `IntentExtractor` Protocol + spawn-isolation discipline with a WORK-SHAPED prompt (is-this-work + a plain title + a candidate stream/project + an optional waits-on party); on extractor-declines, surface NO proposal that turn. Method-call.**
- **Why reuse the Protocol, not re-implement:** the #56 seam already provides the injectable boundary, the bounded spawn-isolated `claude -p`, the hard timeout, the envelope parse, and the fail-soft `IntentExtractUnavailableError` (Lens-1 + `feedback_no_anthropic_api_key`). Intake supplies a different PROMPT (work-shaped, not the onboarding stop/start prompt) — either a sibling extractor method or a second prompt behind the same Protocol; the builder's call.
- **Why fail-soft to NO-proposal (not to a regex):** the #56 onboarding path falls back to a regex distillation because onboarding MUST produce an answer. Intake is the opposite — it is a quality LIFT over ordinary conversation, and the safe failure mode is to say NOTHING (no proposal) rather than risk a regex over-capturing on every turn. Silence on extractor-failure is the don't-nag-aligned default (FBM affirmative-recognition precedent).
- **The default-installed extractor (the wiring call):** mirrors #56 — a `DisabledIntentExtractor`-style default that declines (so intake is opt-in / off until a real extractor is registered) vs a real extractor wired on by production default. RECOMMEND wiring the real extractor on as the production default for intake (the feature is the point), with the disabled default preserved for tests + the off-aggressiveness level.

### D-INTK.5 — Where the proposal/confirm conversation-state lives. **RECOMMEND: the `proposed` work item in the store IS the proposal state — no separate intake-side pending-queue. A live proposal = an open `proposed` item created this/a-recent turn; confirm = transition to `active`; dismiss = transition to `abandoned`; an un-acted proposal stays `proposed` and is the store's own concern (it does not re-nag). Method-call.**
- Why: the store already models `proposed` as "surfaced, not yet committed." A parallel intake-side pending list would be a second source of truth for the same fact (the five-surface-drift anti-pattern the whole architecture kills, §2b). The `proposed` item carries the provenance + candidate placement already; the confirm/dismiss are the store's existing transitions.

## §6 Acceptance criteria (outcome-shape; method-in-AC test passed on each)

Each AC states an *outcome* satisfiable by methods other than the one in mind; each maps to a named test at build time. AC IDs are scope-descriptive (per `feedback_scope_descriptive_ac_ids`).

**AC.INTK.DETECT.1** — Given a conversational turn whose text carries a clear forward-looking piece of work the user mentions (a task, a follow-up, a thing to do, a blocker), intake recognises it as work-intent and produces a candidate (a plain title + an optional candidate stream/project + an optional waiting-on party when the turn names one). Given a turn carrying no work-intent (a question, chatter, a statement of fact), intake recognises NO work-intent and produces no candidate. *(Outcome: work-vs-not discrimination over a real turn; method — which extractor read, what prompt — is the builder's call.)*

**AC.INTK.DETECT.2** — When the intent-extraction seam declines (unavailable, times out, or returns no usable read), intake surfaces NO proposal for that turn and the turn proceeds normally — the failure never propagates and never produces a low-quality over-capture. *(Outcome: fail-soft to silence, the don't-nag-aligned default; method is the builder's call.)*

**AC.INTK.PROPOSE.1** — A detected work item is surfaced as exactly ONE concise plain-language proposal (e.g. "Sounds like a new thing to track — want me to keep it under Money?"), carrying NO internal identifier, lifecycle enum, slug, or path; and is backed by a real work item created in the store's `proposed` (surfaced-not-committed) state with conversation provenance and the candidate stream/project placement. The proposal is NOT a silent commit to `active`. *(Outcome: a single plain proposal + a real `proposed`-state placed item + the no-internal-vocab invariant; method is the builder's call.)*

**AC.INTK.PROPOSE.2** — The proposed item carries provenance identifying it as captured from conversation (an `origin: conversation` pointer, distinct from FIDRAFT-graduated / dev-queue / owner-stated origins) and the turn it was captured from, so its source is recoverable later. *(Outcome: intake provenance is captured at creation — architecture §4a load-bearing for later consolidation; method is the builder's call.)*

**AC.INTK.CONFIRM.1** — A plain-language confirmation of a live proposal promotes the proposed item to `active` (it becomes a real tracked work item the lenses render); a plain-language dismissal abandons it (it does not surface in any lens); an unacted proposal does not re-surface / re-nag on subsequent turns. *(Outcome: confirm→active, dismiss→abandoned, ignore→no-renag, all over the store's existing transitions; method is the builder's call.)*

**AC.INTK.LIGHT.1** — Under the default (light) aggressiveness: a turn that is ordinary chatter or a trivial one-off ("can you reformat this paragraph") does NOT produce a proposal or a tracked item; only a clear forward-looking piece of work does. The number of proposals over a sequence of mixed turns matches the count of genuine work-intent turns, not the turn count. *(Outcome: no-over-capture at the light default, measured over a mixed turn sequence; method is the builder's call.)*

**AC.INTK.LIGHT.2** — The intake aggressiveness is read from the per-user interaction-model (`work-tracking`/`intake-aggressiveness`), defaulting light when no cell is set; setting the cell to `off` produces no proposals on any turn, and setting it to a more-eager value lowers the threshold at which a turn produces a proposal — changing the cell changes the capture behavior without editing intake. *(Outcome: per-user-tunable via #34, light default; method is the builder's call. Mirrors the WMS-D4 per-user dial.)*

**AC.INTK.DEDUP.1** — When a turn mentions a piece of work that closely matches an OPEN work item already in the store (a re-mention), intake does NOT create a second proposal/item for it (it suppresses, or surfaces at most a single quiet "already tracking that"); when a turn mentions a genuinely new piece of work that is not a near-duplicate, it IS proposed. A sequence of re-mentions of one thing yields one tracked item, not a pile. *(Outcome: re-mentions don't duplicate, new work still lands; the match method — string / embedding / LLM — is the builder's call.)*

**AC.INTK.LIVE.1 (OUTCOME-ALTITUDE, `outcome-altitude:true`)** — Through ONE real production turn-path invocation (the live `on_user_prompt_submit` contributor path against the live increment-2 store) with NO pre-arranged state: a turn whose text naturally mentions a piece of work the user needs to do results in exactly ONE correctly-placed `proposed` work item in the LIVE store (right plain title, conversation provenance, a sensible candidate stream/project), surfaced as one plain-language proposal — and, in the SAME run, a turn of pure chatter results in ZERO proposals and ZERO new items. Invokes the production entry points (the turn contributor + the #56 extractor seam + the store `create` API), no fixtures, no pre-arranged tracker state. *(This is the literal "a real conversational turn mentioning a piece of work results in a correctly-proposed work-item in the live store, at the light default, no over-capture" the objective names. Method is the builder's call.)*

## §7 Build steps (method-level guidance only — builder's call per ODD §1.1)

Single-component amendment (`primary-persona`); the objective-tracker store is consumed via its existing API. **On `build/wms-increment-2`.** Shape:
1. Manifest at `docs/plans/wms-increment-3-intake-conversational-work-capture.manifest.yaml` (paired, below); one `components:` entry (`primary-persona`).
2. **Detection (AC.INTK.DETECT.*):** a work-shaped read of `TurnPayload.prompt` composing the #56 `IntentExtractor` (a work-shaped prompt — is-this-work + title + candidate stream/project + waits-on party); fail-soft to no-proposal on `IntentExtractUnavailableError`.
3. **Aggressiveness gate (AC.INTK.LIGHT.*):** read `InteractionModel.cell_or_prior("work-tracking", "intake-aggressiveness")`, default light; gate whether a detected candidate becomes a proposal at all (`off` → never; `light` → clear signals only; `eager` → softer signals).
4. **Dedup (AC.INTK.DEDUP.*):** before proposing, compare the candidate against the OPEN items in the store (`query_projection_view`); suppress a high-confidence near-duplicate (conservative bias — propose when unsure).

## §10 F2 Ruthless Feedback (honest doubts + named design risks)

1. **★ The #56 seam is ONBOARDING-shaped, not work-shaped — intake needs a different read.** *Disagreement:* "compose on the #56 intent-extraction seam" is correct as a PATTERN reuse but understates a real shape gap. *Evidence (Tier-0):* `intent_extract.py`'s `ExtractedIntent` carries `disposition: "stop"/"start"` and its `_EXTRACT_PROMPT` is literally "the user was asked for ONE thing they'd love to STOP or START doing" — an onboarding-specific frame. Work-intake needs is-this-work + a title + a candidate stream/project + an optional waits-on party, NOT a stop/start disposition. *Alternative (D-INTK.4):* reuse the `IntentExtractor` PROTOCOL + the spawn-isolation + fail-soft DISCIPLINE (the load-bearing, reusable parts) with a WORK-SHAPED prompt — either a sibling extractor or a second prompt behind the same Protocol. This is a genuine method fork the builder owns; the halt (§8 #3) fires only if the seam cannot carry a work-shaped prompt without modifying the sealed onboarding contract. Honest framing for Luke: intake reuses the #56 MECHANISM (the right call), not its onboarding PROMPT.

2. **The store surface intake creates into exists ONLY on `build/wms-increment-2`.** *Disagreement:* a build dispatched against `main` would silently find no surface to intake into. *Evidence (Tier-0):* the `belongs_to_project`/`tagged_streams`/`priority`/`blocked` extension + `proposed`-entry-state `create` path are on `build/wms-increment-2` (seal `e0afa9c1`), confirmed absent from `main`. *Alternative:* the build stacks on `build/wms-increment-2` (named in the header + §5 + halt §8 #1, verified as the literal first build check). Increment 2 is sealed-local on its branch but not on `main` — per `feedback_build_forward_on_publish_pending`, stacking the next increment on the sealed branch is correct; the build does not wait for an increment-2 merge to `main`.

3. **Dedup false-merge is a worse failure than a duplicate (the asymmetry that sets the bias).** *Disagreement:* "dedup against existing work items" sounds like a pure win, but an over-aggressive dedup silently DROPS a genuinely-new item that merely sounds similar — the new work vanishes with no surface, which is strictly worse than a visible duplicate the user can dismiss. *Evidence:* the architecture's whole value is no-silent-loss of work; a false-merge IS a silent loss. *Alternative (D-INTK.3):* bias dedup CONSERVATIVE — suppress only on a HIGH-confidence match; propose when unsure. Named so the bias is a conscious owner-visible choice, not a silent threshold.

4. **The light default touches the user EVERY turn — the nag risk is real and is the core UX hazard.** *Disagreement:* intake runs on the turn loop, so a mis-tuned aggressiveness nags the user on ordinary conversation — the exact context-bloat + interruption the dispatch warns against. *Evidence:* the FBM load-filter precedent (`file_memory.py` affirmative-recognition junk gate) exists precisely because per-turn surfaces over-fire by default. *Alternative:* the light default + fail-soft-to-SILENCE (D-INTK.4) + propose-suppress dedup (D-INTK.3) + the #34 `off` level together bound the nag: intake proposes only on a clear affirmative work-intent signal, says nothing on extractor-failure, never re-nags an ignored proposal, and an annoyed user dials it to `off` (or loam learns the preference from repeated dismissals via `apply_override`). The no-over-capture ACs (AC.INTK.LIGHT.1, AC.INTK.LIVE.1's chatter-turn-yields-zero clause) are the structural guard.

5. **Scope-confidence (F4) note.** The intake SHAPE — propose-and-confirm at a light default, composing the #56 seam + the #34 dial, as a keep-pace turn contributor consuming the existing store — is HIGH-confidence (the architecture pinned WMS-D4 light; the seams already exist; the `proposed` lifecycle is the natural seat) and tightly scoped. The two genuinely-open forks left as ★ owner-calls are the aggressiveness default/levels (D-INTK.2) and the dedup behavior/bias (D-INTK.3) — both surfaced with recommendations, method left to the builder, no method locked in ACs. The detection read, the work-shaped prompt, the dedup match algorithm, and the proposal rendering are method-calls left loose. The ACs are outcome-shape; the forks are surfaced.
