## §1 — Summary / TL;DR (plain English, lead)

1. **What ships.** The hands-off loop's terminal "done" stops requiring only *structural presence* (a `compile.sh` + a source file exist) or a trivial `true`, and starts requiring a **behavioral self-check** — a self-constructed functional check the loop derives from the task's plain-language intent and actually runs against the produced artefact. When that behavioral check does NOT pass, the loop **re-drives a bounded number of refine attempts**, carrying the behavioral failure context back to a sub-agent, **under the existing cost/wall ceiling**, **verification-gated each iteration** (anti-erosion). When the bound is exhausted without a passing behavioral check, the loop emits a **definite, evidence-backed honest-negative** (a first-class plan-success outcome, never retried-to-green).

2. **AC families.** `AC.BRC.*` (Behavioral Refine Cycle): BRC.1 behavioral self-check replaces structural-presence/`true` as the "done" gate; BRC.2 failed behavioral check re-drives bounded refinement carrying failure context; BRC.3 each refine iteration is verification-gated (anti-erosion); BRC.4 the behavioral self-check is isolated from the graded scorer (the loop's OWN check, never the benchmark scorer / independent judge); BRC.5 (lead) an end-test produces a definite per-dimension verdict that the loop now crosses the real-outcome line before stopping — honest-negative valid. BRC.6 the generic replacement of the realpb `"true"` `check_command` with a behavioral self-check (the concrete bug fixed generically).

3. **Key decisions baked (recommendation-led, §5).** D-BRC-1 scope shape: **amendment of the handsoff-loop component** (the orchestrator gains a bounded re-drive around the existing `verify`), not a new sealed component — recommended. D-BRC-2 the behavioral self-check is the loop's OWN self-constructed functional check derived from the plain-language intent, structurally provably-not the graded benchmark scorer / independent judge — recommended (this is the AC.RPB.1-class isolation, carried forward). D-BRC-3 the refine re-dispatch is bounded by an explicit finite attempt count AND the existing cost/wall ceiling, whichever binds first — recommended. D-BRC-4 failure context fed back via the existing sub-task brief/`/goal` seam (the surfaced behavioral-check output), composing the Claude-native `/goal` + orchestrator re-dispatch — recommended (Lens 1: no external agent framework). D-BRC-5 a task-supplied runnable reference artefact is probed by the loop's behavioral self-check where one is supplied (diff against reference), permitted not mandated — recommended.

4. **F2 on scope realism (lead).** The *existence* of this gap is **architecturally certain and aggregate-independent** — verified Tier-0 from source this turn (`orchestrator.py:203-244` is a single dispatch + single structural verify with no re-drive; `arms.py:200` is literally `"true"`). The *size* of the score payoff is NOT known and is NOT scoped here — it is the post-aggregate fast-follow the detached 5-task `verdict.json` failure-class map sizes (see §5/§10.4 gap-fix-now vs payoff-size-post-aggregate split). This plan scopes the **gap fix** only; no AC asserts or depends on a payoff magnitude.

## §5 — Acceptance criteria (`AC.BRC.*`, outcome-shape, method-in-AC test passed per-AC)

Method-in-AC test applied per-AC: *can this AC be satisfied by a method other than the one I have in mind? Yes ⇒ tight scope (good). No ⇒ method stated (Lens-3 violation).* The honest-negative is a **first-class valid polarity** on the lead AC (AC.BRC.5) by construction.

### AC.BRC.1 — Terminal "done" requires a behavioral self-check passing, NOT structural presence and NOT a trivial `true`

The loop's terminal "done" decision is gated by a **behavioral self-check**: a self-constructed *functional* check, derived from the task's plain-language intent, that exercises the produced artefact's behavior (it runs the artefact / probes its observable effect), such that a submission which is structurally present (a `compile.sh` + a source file exist) but does **not** behave as the plain-language intent describes is **NOT** reported "done". A check that passes on structural presence alone, or that is satisfied by running `true` / any no-op, does **NOT** satisfy this AC.

- *Ladders to:* both tests (the non-tech user's "did it actually work" is the real-outcome line; a structural-presence "done" fails the primary-persona test — intent was not carried to *working* execution — and the harness test — the toolkit reports done on a non-working artefact).
- *Satisfiability:* satisfiable by a synthesized run-the-artefact-and-assert-observable-behavior check, by a derived input/output probe, by a diff-against-a-supplied-reference probe, by a property-style behavioral assertion — multiple methods. Constrains *behavioral (exercises the artefact) + derived-from-the-plain-language-intent + structural-presence-and-no-op-insufficient*, NOT the check-construction mechanism. Tight. (This is deliberately NOT method-in-AC: the *refine/synthesis mechanism* is the builder's call; the AC pins only the outcome shape that "done" means behaviorally-verified, not structurally-present.)
- *Source it changes:* `orchestrator.py:231` (the single `verify(frozen,...)` becomes behaviorally-gated); `arms.py:200` (`check_command: "true"`) — generically, per BRC.6.

### AC.BRC.2 — A failed behavioral check re-drives a BOUNDED number of refine attempts carrying the failure context

When the behavioral self-check (AC.BRC.1) does **not** pass, the loop does **not** terminate at the first failure: it **re-drives** the work by dispatching a sub-agent again, **carrying the behavioral failure context** (the surfaced output of the failed behavioral check — what was expected vs what the artefact did) into that re-dispatch, for a **bounded, finite number of attempts**. The bound is explicit (a finite attempt count AND the existing cost/wall ceiling, whichever binds first — no unbounded turn-burn). A single-pass dispatch with no re-drive on a failed behavioral check does **NOT** satisfy this AC; an unbounded re-drive loop does **NOT** satisfy it either.

- *Ladders to:* both tests (the loop iterating toward a working outcome instead of stopping at the first failure IS the translation layer doing its job; the bound keeps the toolkit item from burning unbounded cost — a poisoned toolkit item).
- *Satisfiability:* satisfiable by a `while not done and attempts < N and within_budget:` re-dispatch loop, by a judge-driven re-plan with a finite-attempt stop, by a recursive single-step decomposition with a bounded retry — multiple methods. Constrains *failed-behavioral-check → re-dispatch-with-failure-context + explicitly-bounded (attempts AND cost/wall ceiling) + not-single-pass + not-unbounded*, NOT the loop construct or the context-marshalling format. Tight.
- *Source it changes:* `orchestrator.py:203-244` (the single `for` pass + single `verify` becomes a bounded re-drive around `verify`); composes the existing `/goal` + `_dispatch_subagent` + sub-task-brief seam (`goal_drive.py`, `orchestrator.py:125-163`).

### AC.BRC.3 — Each refine iteration is verification-gated (anti-erosion, a binding constraint not a footnote)

Every refine iteration's continuation is **gated by a verification step** — an iteration may only be accepted/continued on the basis of a check result, never on the sub-agent's unverified self-report that it improved. The loop does **not** accept "I fixed it" prose as progress; the behavioral self-check (or an equivalent verification) decides whether an iteration advanced the work, and a refine pass that does not improve the verifiable outcome does not silently accumulate (long-horizon unguided iteration degrades quality — SlopCodeBench-class; this is folded as a binding constraint). An iteration accepted on unverified self-report does **NOT** satisfy this AC.

- *Ladders to:* harness test (an unguided refine loop that degrades quality over iterations is a poisoned toolkit item; the verification gate is what keeps "refine" from being "drift"). Composes the existing "loam's independent check decides — NOT the self-reports" spine (`orchestrator.py:230`, `verify.py:177-181`).
- *Satisfiability:* satisfiable by the behavioral self-check gating every iteration, by a per-iteration verify exit-code gate, by a judge-`needs_fresh_start`-style drift-detection verdict that discards a diverged chain (Lens 5 restart-not-continue), by a monotonic-improvement gate — multiple methods. Constrains *every-iteration-verification-gated + no-unverified-self-report-progress + anti-erosion-binding*, NOT the gating mechanism. Tight.
- *External corroboration (web-research per-part, §6):* SlopCodeBench (arXiv 2603.24755) — quality erodes across ~80% of trajectories under unguided long-horizon iteration → **ADOPTED AS A BINDING CONSTRAINT** (this AC), not a footnote; the mechanism stays the builder's call.

### AC.BRC.4 — The behavioral self-check is the loop's OWN self-constructed check, provably NOT the graded scorer / independent judge

The behavioral self-check (AC.BRC.1) that decides the loop's "done" is the loop's **own self-constructed** check; it is **provably distinct** from (a) the graded benchmark scorer (the real upstream `programbench eval`), and (b) the independent held-out adversarial judge (`handsoff_loop_goal_refine_reharden`'s `_independent_judge` / the realpb scorer's `independent_judge`), and (c) the loop's own intake faithfulness judge (`intake.py:_judge_faithful`). The self-check never consumes the frozen graded acceptance (the `FrozenAcceptance.assert_unseen_by` freeze-isolation spine is preserved — the loop cannot have been steered to the graded test). A behavioral self-check that IS, calls, or imports the graded scorer / the independent judge does **NOT** satisfy this AC.

- *Ladders to:* both tests (a loop scored by the thing that grades it is not an honest measurement; the loop's autonomy requires it decide "done" by its OWN check, while the graded truth stays external — AC.RPB.1-class isolation).
- *Satisfiability:* satisfiable by a self-check construct in its own module with no import of the scorer/judge (asserted by an AST/import test), by a structurally separate process the orchestrator owns, by an identity/provenance assertion the freeze path enforces — multiple methods. Constrains *loop's-own + provably-not-the-scorer + provably-not-the-independent-judge + provably-not-the-intake-judge + freeze-isolation-preserved*, NOT the separation technique. Tight.
- *Scope note (F2):* this is the AC that keeps the change honest. If the builder finds the behavioral self-check **cannot** be isolated from the graded scorer without breaking the loop's autonomy, that is the §8 halt-trigger — surface the tension with file evidence, do NOT silently couple them.

### AC.BRC.5 — End-test: a definite per-dimension verdict that the loop crosses the real-outcome line before stopping (lead AC; honest-negative valid)

An end-test produces a **definite, evidence-backed per-dimension verdict table** demonstrating, on a real (non-toy) task of probe-class-or-harder, that: (i) the loop's terminal "done" is gated by a behavioral self-check, not structural presence (a structurally-present-but-behaviorally-wrong artefact is NOT reported done); (ii) a failed behavioral check re-drove a bounded, failure-context-carrying refinement (the re-dispatch is observable in the transcript/artefacts; the bound held); (iii) each refine iteration was verification-gated (no unverified-self-report progress accepted); (iv) cost/wall stayed within the existing ceiling (measured, not estimated, via the existing `--output-format json` cost surface) — **OR** a definite, evidence-backed honest-negative naming *why* a dimension could not be demonstrated. A definite honest-negative ("the behavioral-refine cycle did not improve the outcome on this task — here is the evidence") **satisfies this AC exactly as a positive does**, is reported straight, and is **NEVER retried to green, NEVER the bound weakened, NEVER widened into re-running until it passes** (F2 / `feedback_locked_design_not_license`).

- *Ladders to:* both VALUE_PROPOSITION tests jointly — the prime-objective-level deliverable: the loop now carries intent to *working* execution by iterating, or names honestly why it could not on the chosen task.
- *Satisfiability:* "a definite, evidence-backed per-dimension verdict on a real task exists, either polarity" — satisfiable by any independent dimension-grounded verdict method; not green-only, not method-bound. The honest-negative is a constructed valid polarity, not an exception.
- *Scope note (gap-fix vs payoff-size, F2 §10.4):* this AC verifies the **gap is closed** (the loop is now architecturally capable of behavioral iteration) — it does **NOT** assert or measure a benchmark-score *magnitude*. The score-payoff size is the **post-aggregate fast-follow** the detached 5-task `verdict.json` failure-class map sizes; it is explicitly NOT an AC of this cycle and no AC depends on a payoff number.

### AC.BRC.6 — The realpb in-loop `check_command: "true"` is replaced by the behavioral self-check, generically

The concrete defect — the realpb arm wiring sets the loop's in-loop `check_command` to literally `"true"` (`arms.py:200`), so the loop's keep-going condition is satisfied by a no-op — is fixed by routing the loop's in-loop check through the **generic behavioral self-check construct** (AC.BRC.1/.4), **not** by a realpb-specific hack and **not** by hand-authoring a per-task `"true"`-replacement string. The replacement is generic: the same construct serves any task driven through the loop (the realpb arm is one consumer). A fix that special-cases realpb, or substitutes another no-op / structural-only command, does **NOT** satisfy this AC.

- *Ladders to:* harness test (the concrete bug that makes the loop's "done" a no-op for the real benchmark is the sharpest instance of the gap; fixing it generically is the toolkit improvement, fixing it realpb-specifically would be a non-objective patch).
- *Satisfiability:* satisfiable by the realpb arm consuming the generic behavioral-self-check construct, by the orchestrator constructing the behavioral check from the objective when the caller supplies a no-op/absent `check_command`, by a check-command-derivation seam the arm wiring delegates to — multiple methods. Constrains *the-`"true"`-literal-is-replaced + by-the-generic-construct + not-realpb-specific + not-another-no-op*, NOT the wiring technique. Tight.
- *Source it changes:* `framework/tools/programbench-revival/src/programbench_revival/arms.py:200` (consumed-by-the-harness; the generic construct is in the handsoff-loop package).
