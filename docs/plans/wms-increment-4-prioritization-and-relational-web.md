## §1 Summary / TL;DR

**What ships (increment 4 only):** TWO functions, both DERIVATION + SURFACING over the inc-2 store, no new storage.

1. **PRIORITIZATION (WMS-D5) — a derived, TRANSPARENT, calibrate-on-use ordering.** A work item's rank is COMPUTED from multiple signals — the existing `tracker_context` priority-key, dependency/blocking-impact (how much downstream work an item unblocks — read off the EXISTING edge graph), goal-alignment (does it ladder up to a user-objective — read off `OBJECTIVES.md`), recency/staleness (the EXISTING `last_transition_at`), and explicit owner pin/defer overrides. The blend is TRANSPARENT — every ranked item carries a plain-language *reason* ("next because the launch is waiting on it"), never a black-box score — and the weighting is CALIBRATE-ON-USE (a tunable signal-weight set, the same Lens-4 no-magic-number discipline as #34's thresholds), not an imported constant. User pins always override.
2. **The RELATIONAL WEB, SURFACED.** Inc-2 built the edge graph + the `unblocked_next`/`waiting_on_other` queries; inc-4 turns them into the answers that make the graph valuable, rendered concisely in a per-turn lens: **what's unblocked and ready to do next** (the prioritized `unblocked_next` output), **what's blocked and on what** (the `blocks`/`waits_on` chain in plain language), **what's waiting on ME vs on OTHERS** (`owner_pending`/internal vs external-`party` `waits_on`), and the **decomposition tree** (the `parent`/`child` ladder). One concise block, the Slice-D char-cap + TTL + fail-soft discipline — no bloat.

**The two compose:** the relational lens's "what's next" row is the PRIORITIZED `unblocked_next` output with its transparent reason — prioritization is what makes "next" mean *the right* next thing, and the relational web is what gives prioritization the dependency/blocking-impact signal. They ship together because each is half of "what should I do next, and why."

**AC families:**
- `AC.PRI.*` — derived priority: a multi-signal ordering over the open work set; the ordering changes when a signal changes (a newly-unblocking item rises); user pin/defer overrides; calibrate-on-use weighting (changing the weights changes the order without code edits); NO black-box — every ranked item carries a transparent reason.
- `AC.REL.*` — relational-web surfacing: unblocked-next, blocked-on-what, waiting-on-me-vs-others, and the decomposition tree, each answered from the EXISTING queries + edges, rendered in plain language with no internal vocab.
- `AC.SURF.*` — the per-turn relational lens: one concise capped block composing the Slice-D renderer discipline + the prioritized next + the relational answers, fail-soft, registered as a `TriggerKind.turn` contributor; no per-turn latency regression.
- `AC.WMS4.LIVE.*` — **outcome-altitude**: a real store with a real dependency chain (no pre-arranged surfacing state) → the prioritization surfaces the RIGHT unblocked-next item AND a transparent plain-language reason, over the production entry points.

**Key decisions baked (full list + recommendations in §3):**
1. **EXTEND the keep-pace derivation/lens layer — do NOT build a new component, do NOT touch the store** (§3 D-PRI.1). The store already holds edges + priority + the queries; inc-4 is a derivation module + a relational lens beside `projects.py`/`intake.py`, consuming the existing query API.
2. ★ **WMS-D5 — the priority SIGNAL SET + their relative WEIGHTING** (§3 D-PRI.2). RECOMMEND a five-signal blend (priority-key · blocking-impact · goal-alignment · staleness · explicit-pin) with **calibrate-on-use weights** and pins as a hard override. The signal SET being product-shape-complete is the genuine ★OWNER call; the numeric weights are a calibratable method-default, not an owner constant (§10 RF #1 draws the line).
3. ★ **The "unblocked-next" surfacing shape** (§3 D-PRI.3) — RECOMMEND surfacing the SINGLE top prioritized unblocked item as "the next thing" with its reason, plus a short "also ready" tail, rather than a flat dump of all unblocked items. A genuine product-shape call (how much loam volunteers per turn).
4. **Transparency mechanism: a structured per-item reason, not a numeric score** (§3 D-PRI.4, method-call). The score is internal; what surfaces is the plain-language *why* (Lens-2 — the non-tech trust value).
5. **Graph self-heal against FBM STATE (#71) is the DERIVE-priority-uses-STATE slice ONLY; the full edge-mutation self-heal is OUT of scope** (§3 D-PRI.5 + §10 RF #2). Inc-4 READS FBM STATE as a priority signal; it does NOT mutate the edge graph against ground truth (that is #71, a separate seam).

**F2 RF on scope realism (full treatment in §10):** (1) the WMS-D5 signal-set-vs-weights line — the signal SET is the owner call, the numeric weights are calibratable method-defaults; conflating them would either over-ask Luke (weights) or under-ask (the set). (2) The architecture (§7 row 4) names "graph self-heal against FBM STATE (deviation→#71)" as part of inc-4 — but #71 is PENDING and is a distinct edge-mutation seam; inc-4 takes only the read-STATE-as-a-signal slice and explicitly defers the edge-mutation self-heal, to keep the increment honest and single-component. (3) Half the projects still have no FBM ground-truth STATE (loam+cairn only) — the blocking-impact + staleness signals carry the rest; the STATE signal is a bonus where available, never load-bearing.

## §3 Named decisions (with recommendations) — surface to Luke

Every decision carries a recommendation. ★ flags a genuine **owner product-shape call** (it changes the ranking the user lives with, or how much loam volunteers); the rest are **autonomous method-calls** (the builder takes method from here).

### D-PRI.1 — Extend the keep-pace derivation/lens layer vs a new component. **RECOMMEND: EXTEND `primary-persona` keep-pace (a new `prioritize.py` derivation + a new `relational.py` lens) — do NOT build a new component, and do NOT modify the objective-tracker store. Method-call (the architecture + the existing queries already rule the shape).**
- **Why extend, not new:** every primitive inc-4 needs ALREADY EXISTS and is consumed READ-ONLY — the edge graph + `unblocked_next`/`waiting_on_other` (inc-2 runtime), the `priority` field + `last_transition_at` (inc-2 projection), the `tracker_context` priority-key, the `OBJECTIVES.md` ladder, the Slice-D renderer, the `TriggerKind.turn` seat. Inc-4 is derivation + surfacing OVER those — the same keep-pace shape `projects.py` (inc-2) and `intake.py` (inc-3) already established. A new component would re-create the turn-loop wiring + contributor registration the keep-pace surface owns (Lens-1: compose, don't duplicate).
- **Why NOT touch the objective-tracker store:** the dispatch is explicit — the edge/priority STORAGE exists from inc-2; inc-4 is derivation + surfacing ON TOP. The store is a pure CONSUMER target (its `unblocked_next`/`waiting_on_other`/`query_projection_view`/`trace_to_root` read API + the `priority` projection field). This keeps inc-4 single-component (`primary-persona` only). **If derivation discovers it needs a store-side change** (e.g. blocking-impact needs a query the runtime does not expose, or a pin needs a store field that does not exist), it HALTS rather than silently amending the sealed store (§8 #2).
- **Alternative rejected:** a standalone `prioritization` component. Rejected — duplicates the turn-loop + contributor seam and splits the prioritization derivation from the relational lens that consumes it (they ship as one coherent "what's next + why").

### D-PRI.2 — The priority SIGNAL SET + their WEIGHTING. ★ **RECOMMEND: a FIVE-signal blend — (1) the existing `tracker_context` open-loop priority-key, (2) blocking-impact (how much downstream work the item unblocks, off the edge graph), (3) goal-alignment (ladders up to a user-objective), (4) recency/staleness (`last_transition_at` past cadence), (5) explicit owner pin/defer as a HARD override above the blend — with CALIBRATE-ON-USE weights (a tunable weight set, no imported magic number, Lens-4). The SIGNAL SET being product-shape-complete is the genuine owner call; the numeric weights are a calibratable method-default (§10 RF #1 draws the line). Worth Luke's deliberate eyeball — the signal set defines what "important" MEANS for his work.**
- **Why these five:** they are exactly the architecture §4b inputs ("the user-objective the item ladders up to · dependency position · staleness against cadence · explicit owner pins/defers · the `tracker_context` open-loop priority-key"), each now buildable because inc-2 shipped the substrate (edges → blocking-impact; `OBJECTIVES.md` → goal-alignment; `last_transition_at` → staleness; the existing key → signal 1). No speculative signal beyond the architecture's named set.
- **Why pins are a HARD override, not just signal 5:** architecture §4b — "the user can always override." A pin is an owner instruction, not a weighted hint; "Money is the priority right now" must float Money items regardless of the computed blend (the locked-design-not-license principle's inverse — the owner's explicit call beats the derivation). RECOMMEND pin = hard override; defer = hard demote.
- **The calibrate-on-use weighting (Lens-4):** the relative weight of each signal is a tunable set the build picks a sensible default for and that calibrates on real use — NOT an imported constant and NOT an owner-ruled number. Same discipline as #34's thresholds. **The owner call is the SIGNAL SET (is five the right set — anything missing, anything over-built?), NOT the weights** (those are method + calibration). Recommendation: the five-signal set with pins as a hard override, weights calibrate-on-use.

### D-PRI.3 — The "unblocked-next" surfacing shape. ★ **RECOMMEND: surface the SINGLE top prioritized unblocked item as "the next thing" with its transparent reason, plus a SHORT "also ready" tail (the next 1–2), rather than a flat dump of every unblocked item. Worth Luke's eyeball — it sets how much loam volunteers per turn (the every-turn surface budget).**
- **Why one-plus-a-tail, not a dump:** the architecture's on-my-plate lens answers "what should I look at now" — a single clear next thing is the non-tech-aligned answer (decision fatigue is the failure mode a dump creates). The relational lens is per-turn and char-capped (Slice-D 600); a flat list of all unblocked items both blows the cap and re-creates the status-anxiety the system exists to fix. The single top + a short tail gives "here's the one thing, and a couple more if you want."
- **The honest tension (F2):** a single "next" can be wrong if the prioritization mis-ranks — so the reason is load-bearing (the user can see WHY it's next and correct it). RECOMMEND the single-top-plus-tail WITH the transparent reason on the top item, so a mis-rank is visible and correctable, not silent. The owner call: confirm single-top-plus-short-tail (vs a flat unblocked list, vs top-only-no-tail).

### D-PRI.4 — The transparency mechanism. **RECOMMEND: a STRUCTURED PER-ITEM REASON (plain language), NOT a surfaced numeric score. The blend produces an internal ordering; what reaches the user is the dominant-signal *why* ("next because the launch is waiting on it" / "next because it's been stale two weeks and nothing's blocking it"). Method-call — but the OUTCOME (every ranked item carries a plain-language reason; no black-box score reaches the user) is an AC (AC.PRI.4, AC.WMS4.LIVE.1).**
- **Why a reason, not a score:** Lens-2 — the non-tech trust value IS the explainability ("this is next because X is waiting on it"). A surfaced number ("priority 0.83") is exactly the black-box the architecture §4b + WMS-D5 forbid ("NOT a black-box score"). The dominant contributing signal becomes a plain-language clause; the numeric blend stays internal.
- **Why this is mostly method:** which signal "dominates" and how the clause is phrased is the builder's call; the load-bearing OUTCOME (a transparent reason accompanies the ranking, no raw score surfaces) is the AC. The zero-internal-vocab invariant (work_visibility precedent) carries — no IDs/enums/scores in the reason text.

### D-PRI.5 — Graph self-heal against FBM STATE — scope line. **RECOMMEND: inc-4 READS FBM `derive_project_state` as a PRIORITY SIGNAL ONLY (a project whose ground-truth STATE shows its work landed can DEMOTE that project's stale-looking items); inc-4 does NOT MUTATE the edge graph against FBM ground truth — the full edge-mutation self-heal is #71, a distinct seam, OUT of scope. Method-call on the read-slice; the deferral is the F2 scope-honesty call (§10 RF #2).**
- **Why only the read-slice:** the architecture §7 row 4 names "graph self-heal against FBM STATE (deviation→#71)" under inc-4, but #71 ("memory-reality mismatch side-channel — structured surface + ground-truth auto-correct") is PENDING and is an edge-MUTATING reconciliation seam (it would `clear_edge`/transition items against ground truth). That is a write-path against the sealed store + a whole correctness surface of its own. Inc-4's honest deliverable is the READ-slice: FBM STATE as one input to the priority blend where a project is FBM-bound (loam/cairn today). Building the full mutation self-heal here would silently widen inc-4 into #71's scope and open a store-write path (§8 #2 halt).
- **The owner-visible framing:** inc-4 delivers transparent prioritization that USES ground-truth STATE where available; the auto-correcting graph self-heal (mutating edges/states against reality) stays the named #71 follow-on. Honest, not silently dropped.

## §6 Acceptance criteria (outcome-shape; method-in-AC test passed on each)

Each AC states an *outcome* satisfiable by methods other than the one in mind; each maps to a named test at build time. AC IDs are scope-descriptive (per `feedback_scope_descriptive_ac_ids`).

**AC.PRI.1** — Over a set of open work items, the prioritization produces an ORDERING that reflects more than one signal: given two items equal on the existing `tracker_context` priority-key, the one that unblocks more downstream work (more `blocks`/`waits_on` edges resolve when it lands) OR the one that ladders up to a user-objective OR the one that is staler past its cadence ranks ahead — i.e. the order is NOT determined by the single open-loop key alone. *(Outcome: a multi-signal ordering; method — the blend function — is the builder's call.)*

**AC.PRI.2** — The ordering is RESPONSIVE to a signal change: recording an edge that makes a previously-blocked item unblock-many (or an item passing its staleness cadence, or being placed under an objective) changes its rank in the next derivation — without editing the prioritization code. *(Outcome: derived-not-static, verifiable by changing the graph/state; method is the builder's call.)*

**AC.PRI.3** — An explicit owner PIN floats its target above the computed blend (a pinned item/project ranks first regardless of its computed signals), and a DEFER demotes its target below; removing the pin/defer returns the item to its computed rank. *(Outcome: pins are a hard override per architecture §4b; method — where the pin is read from — is the builder's call.)*

**AC.PRI.4** — Every ranked item carries a PLAIN-LANGUAGE reason for its position (e.g. "next because the launch is waiting on it" / "stale two weeks and nothing's blocking it"), and NO raw numeric priority score is surfaced to the user. The reason names the dominant contributing signal in plain language, carrying no internal identifier, lifecycle enum, slug, path, or score. *(Outcome: transparent-not-black-box — the Lens-2 trust value + the zero-internal-vocab invariant; method — how the dominant signal is selected + phrased — is the builder's call.)*
