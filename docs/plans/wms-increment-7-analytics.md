## §1 Summary / TL;DR

Increment 7 is the LAST WMS increment: **analytics — a SMALL, CONSERVATIVELY-SCOPED set of genuinely-actionable insights derived read-only over the work-item event log + projection, surfaced ON-DEMAND in plain language, transparent (like the prioritization reasons).** It builds NO new store, no new field, no new event kind, and — critically — NO new always-on per-turn block. It is one new keep-pace module on `primary-persona` composing the inc-2 event log + projection read-only (Lens 1).

**★ The load-bearing honesty up front (F2 — this is what the architecture flagged as the lowest-confidence increment, and the F2 the brief made load-bearing):** most "work analytics" a dashboard would show are VANITY metrics for a single person tracking their own work — they look like insight but do not change what the user does next (the Lens-2 test). I have scoped this increment HARD to the few that pass that test, and I am explicitly CUTTING the rest. My honest read is below (§3 D-ANL.1) and the recommendation is **SHIP THE CONSERVATIVE FEW, NOT A DASHBOARD** — and if the owner wants it even smaller, the minimal viable shape (the single pile-up insight) is named and defensible.

**The three insights that pass the "changes what the user does next" test (RECOMMEND ship):**

1. **Where work is piling up / stalling** (the WHERE-is-it-stuck insight) — which project / stream / goal has accumulated the most open, non-advancing work (open items grouped by project/stream, ranked by count + collective staleness). *Changes behaviour:* it tells the user where to point attention next — "your Money stream has six things sitting and nothing's moved in two weeks." This is the single most actionable analytic for a person tracking their own work; it is the one I'd keep if forced to one.
2. **Chronically blocked / waiting items** (the WHAT'S-STUCK-ON-SOMETHING-ELSE insight) — items that have been `blocked` or `waits_on` an external party for longer than a staleness threshold. *Changes behaviour:* it surfaces the thing the user forgot was waiting on someone — "the launch has been waiting on Eric for nine days." A direct nudge to chase or re-route.
3. **Completion-vs-intake balance** (the AM-I-KEEPING-UP insight) — over a recent window, how many items were captured vs finished. *Changes behaviour:* a single honest signal of whether the user is accumulating faster than they finish — "you've added eleven things and finished three this week." It tells the user to stop capturing and start closing, or that they're on top of it. ONE plain sentence, not a chart.

**The vanity metrics I am explicitly CUTTING (RECOMMEND defer/never — §3 D-ANL.2):** raw throughput-as-a-number ("you completed 7 items"), velocity trends / burndown charts, cycle-time-as-a-headline-statistic, per-stream bottleneck-edge counts ("this item blocks 4 others" — the relational lens already surfaces this where it's actionable), and any time-series / dashboard view. These are number-theatre for a single person: they do not tell the user what to DO. Cycle-time is kept ONLY as a *supporting* phrase inside insight #1 (how long the pile has been sitting), never as a headline metric.

**AC families:** AC.ANL.PILEUP.* (insight 1 — where work accumulates/stalls, grouped + ranked, plain-language, off the projection) · AC.ANL.STUCK.* (insight 2 — chronically blocked/waiting items past a staleness threshold, off the edge graph + lifecycle) · AC.ANL.BALANCE.* (insight 3 — completion-vs-intake over a window, derived off the event log) · AC.ANL.SURFACE.* (on-demand only — NOT a per-turn contributor; char-capped; zero-internal-vocab; honest-empty when there's no data; transparent — every insight names WHY it's flagged) · AC.WMS7.LIVE.1 (the outcome-altitude — a real store with real transition history → the chosen analytic produces a correct, plain-language, actionable insight live through the production entry point, no pre-arranged state).

**Key decisions baked:** the insight SET is the conservative three above, vanity metrics cut (D-ANL.1/.2 — ★OWNER, the central call); analytics is ON-DEMAND, never a new per-turn block (D-ANL.3 — the architecture mandate, autonomous); it derives over the event log + projection read-only, no new store/field/event-kind (D-ANL.4 — Lens-1, autonomous); cycle-time is a supporting phrase, never a headline metric (D-ANL.5 — autonomous, falls out of the vanity cut); the staleness/window thresholds are calibrate-on-use method-defaults, not owner constants (D-ANL.6 — the F4 scope↔confidence line, autonomous).

**F2 scope realism:** this is a SINGLE-component increment on a sealed component, composing two built read-only surfaces (the event log + the projection) that already carry every datum the three insights need — no store change, no new query, no new event kind. The build SURFACE is small (one `analytics.py` module with three derivation functions + one on-demand render). **The genuine risk is NOT build-size — it is OVER-BUILDING: shipping a dashboard of vanity metrics that look impressive and change nothing.** The conservative-scope cut (§3) is the load-bearing design act of this increment, and the ★OWNER decision is precisely "is the conservative three the right set, or do you want it even smaller." I name the minimal-viable shape (insight #1 alone) so the owner can cut further without re-planning.

## §6 Acceptance criteria (outcome-shape; method-in-AC test passed on each)

Each AC states an observable OUTCOME; the method that satisfies it is the builder's call. The method-in-AC test (can the AC be satisfied by a method other than the one I have in mind?) passes on each.

**AC.ANL.PILEUP — insight 1: where work is piling up / stalling**
- **AC.ANL.PILEUP.1** — Given a work-item set where one project (or stream, or goal) holds materially more open, non-advancing items than the others, the pile-up insight names that project/stream as the place work is accumulating, with the count of open items. (Outcome: the most-accumulated group is correctly identified + named. The grouping + ranking mechanism is the builder's call.)
- **AC.ANL.PILEUP.2** — The pile-up insight is TRANSPARENT: it names WHY the group is flagged in plain language — the count and how long the work has been sitting (the supporting cycle-time phrase, D-ANL.5) — never a bare number or a black-box score. ("Six things under Money, and nothing's moved in two weeks.") (The transparent-reason outcome, mirroring the inc-4 prioritization-reason discipline.)
- **AC.ANL.PILEUP.3** — A work-item set with no meaningful accumulation (work spread evenly, nothing stalled) produces an honest no-pile-up result — the insight does NOT fabricate a "hottest" group when there is no real signal. (The honest-empty outcome — no manufactured insight.)

**AC.ANL.STUCK — insight 2: chronically blocked / waiting items**
- **AC.ANL.STUCK.1** — Given items that have been in `blocked` status or carry an external-party `waits_on` edge for longer than the staleness threshold, the stuck insight names them with what they are waiting on, in plain language. ("The launch has been waiting on Eric for over a week.") (Outcome: the chronically-stuck items surface with their blocker. The threshold + the edge/lifecycle read are the builder's call.)
- **AC.ANL.STUCK.2** — Items that are blocked/waiting but BELOW the staleness threshold (recently blocked, normal) do NOT surface in the stuck insight — only the chronic ones. (The chronic-not-all outcome — the insight is the forgotten-waiting nudge, not a dump of every blocked item, which the relational lens already shows.)
- **AC.ANL.STUCK.3** — A work-item set with nothing chronically stuck produces an honest empty result for this insight — no fabricated "stuck" item. (The honest-empty outcome — AC.ANL.SURFACE.3 applied to this insight.)

**AC.ANL.BALANCE — insight 3: completion-vs-intake balance**
- **AC.ANL.BALANCE.1** — Over a recent window, the balance insight reports, in one plain sentence, how many items were captured vs how many reached a terminal/done state — derived over the event log's `ObjectiveCreated` vs terminal `StatusTransitioned` events in the window. ("You've added eleven things and finished three this week.") (Outcome: an honest capture-vs-finish signal over the window. The event-log walk + the window are the builder's call.)
- **AC.ANL.BALANCE.2** — The balance insight is DERIVED OVER HISTORY, not over current state: it reads the event log's creation + terminal-transition events within the window, NOT a snapshot count — so an item created and finished within the window counts in both. (The event-history-derivation outcome — the load-bearing Lens-1 fact that analytics rides the event log, verifiable: the result reflects transitions that the current-state projection alone cannot reconstruct.)
- **AC.ANL.BALANCE.3** — A window with no activity produces an honest "nothing captured or finished" result, not a fabricated or misleading ratio (no divide-by-zero theatre). (The honest-empty outcome.)

**AC.ANL.SURFACE — the on-demand surface + the cut**
- **AC.ANL.SURFACE.1** — Analytics is ON-DEMAND: the `render_analytics_block` production entry point renders the insights when invoked, and analytics registers NO `TriggerKind.turn` contributor — no new always-on per-turn block exists after this increment. (The on-demand outcome — D-ANL.3 / the architecture mandate. Verifiable: the per-turn registration set is unchanged from inc-6; analytics adds zero turn blocks.)
- **AC.ANL.SURFACE.2** — Every surfaced insight carries zero internal vocabulary: no IDs, slugs, paths, enums, event kinds, or numeric scores — plain-language sentences a non-tech user reads directly. (The zero-internal-vocab HARD invariant, mirroring every WMS lens render.)
- **AC.ANL.SURFACE.3** — The whole analytics block is char-capped via the shared `finalise_block` discipline and degrades fail-soft: a store/event-log read error yields an empty/“no analytics available” result without raising, never wedging the caller. (The capped + fail-soft outcome, reusing the Slice-D discipline.)
- **AC.ANL.SURFACE.4** — The surface contains ONLY the conservative insight set (pile-up, stuck, balance) — it does NOT render raw throughput-as-a-number, a velocity/burndown trend, a cycle-time-headline statistic, a per-item bottleneck-edge count, or any chart/time-series. (The vanity-cut outcome — D-ANL.2 made checkable: the render surface is the three actionable insights and nothing beyond them.)

**AC.WMS7.LIVE — the outcome-altitude AC** (`outcome-altitude: true`)
- **AC.WMS7.LIVE.1** — Against a REAL work-item store (an isolated fixture DB) carrying a REAL transition history — items created at different times, some advanced to done, some left stalled, some blocked/waiting past the threshold, intake outpacing completion in the window — and with NO pre-arranged analytics/insight state: the live `render_analytics_block` production entry point, reading the live event log + projection, produces (a) a correct pile-up insight naming the genuinely-most-accumulated group with its plain-language reason; (b) a correct stuck insight naming the chronically-waiting item(s) with what they wait on; (c) a correct completion-vs-intake sentence derived over the event-log history in the window — all in plain language, char-capped, zero internal vocabulary, with NO per-turn registration and NO mocks at the store/event-log boundary. (The brief's named outcome-altitude: a real store with history → the chosen analytics produce a correct, plain-language, actionable insight LIVE through the production entry point, no pre-arranged state.)

## §8 Halt triggers (abort the in-flight build + surface)

1. **No work model to analyze.** If BASELINE resolves to a tree without the inc-2 work-item store + event log + the lenses (e.g. an accidental main-based build), HALT — there is no history to derive analytics over. (The §11 predecessor check is the pre-build guard.)
2. **A needed store-side change.** If a derivation needs a query the runtime does not expose, a projection field that does not exist, a new event kind, OR any store/event MUTATION, HALT and surface — do NOT open a sealed objective-tracker amendment inside this increment. The three insights are designed to ride the EXISTING `all_events()` + projection API; if one cannot, that insight is re-scoped or cut, not bolted onto the store.
3. **The always-on temptation.** If the build is about to register an analytics block as a `TriggerKind.turn` contributor (an always-on per-turn surface), HALT — analytics is ON-DEMAND by architecture mandate (D-ANL.3); an always-on analytics block inverts the increment and re-bloats the surface inc-6 slimmed.
4. **The dashboard-creep temptation.** If the build is about to add a vanity metric the plan CUT (raw throughput number, velocity/burndown, cycle-time headline, bottleneck-edge count, a chart/time-series), HALT — those are explicitly out of scope (D-ANL.2 / AC.ANL.SURFACE.4); re-adding one needs an owner ruling, not a builder's "while I'm here."
5. **Surrounding ODD violation.** If the build discovers an ODD violation in the surrounding inc-2..inc-6 code (unnamed-case code, a method-in-AC), surface it — do NOT silently extend it (the subagent-ODD-halt discipline).
6. **The data-isn't-there honesty halt.** If, on reading the live event log, the historical data needed for an insight turns out NOT to be reconstructable read-only (e.g. terminal transitions are not timestamped in a way that supports the window), HALT and surface — do NOT fabricate the insight or silently widen the store to record it. Re-scope the insight to what the data honestly supports, or cut it, and say so.

## §10 F2 Ruthless Feedback (honest doubts + named design risks)

**RF #1 — analytics' marginal value here is genuinely LOW, and the honest recommendation is conservative-or-minimal, not a dashboard (the load-bearing F2).**
- *Disagreement with the implicit "build analytics" framing:* the architecture itself flagged this as the lowest-confidence increment (§7 row-7, WMS-D6: "which analytics a non-tech user actually wants is unverified — don't build speculatively"). The honest read is that for ONE person tracking their OWN work, MOST of what "analytics" connotes (throughput, velocity, cycle-time charts) is vanity — it reports numbers that do not change behaviour.
- *Evidence:* the Lens-2 test (VALUE_PROPOSITION primary-persona test, the WMS prime objective per `feedback_value_proposition_as_prime_objective`): a feature earns its place only if it reduces the user's translation burden / changes what they do next. A throughput count fails it; "your Money stream has six things stalled" passes it.
- *Alternative:* ship the conservative THREE that pass the test (D-ANL.1), CUT the vanity metrics for good (D-ANL.2), and name the minimal-viable shape (insight #1 alone) so the owner can cut further. If the owner reads this and concludes analytics isn't worth even three right now, deferring to insight #1 — or deferring the whole increment until a real user asks an analytics question — is a fully defensible call I'd support. This is named as the ★OWNER decision, not silently resolved.

**RF #2 — the pile-up insight overlaps the streams/projects lenses; is it redundant?**
- *Disagreement with my own design:* the streams lens (inc-1) and projects lens (inc-2) already surface per-stream / per-project state; "where is work piling up" could look like a re-render of those.
- *Evidence:* the lenses surface CURRENT state per group (what's in each stream now); they do NOT rank groups by accumulation-over-time or surface the staleness-weighted "this is where work is silently stalling" signal. The pile-up insight is the AGGREGATE-across-groups + temporal view the lenses don't give (architecture §4d: "lenses with a temporal/aggregate grouping").
- *Alternative:* keep the pile-up insight focused on the cross-group RANKING + staleness ("of all your work, THIS is where it's accumulating") — the thing no single lens answers — and lean on the lenses for within-group detail. If in build it proves to be a pure re-render of an existing lens with no added ranking/temporal signal, that is the halt-and-surface case (it would mean the insight adds nothing), and I'd cut it down to #2/#3.

**RF #3 — the staleness/window thresholds are guesses until real use.**
- *Disagreement with my own design:* "chronically" waiting, "stalling," the intake window — the numeric thresholds are chosen ahead of any real data (no user has run analytics over their work yet).
- *Evidence:* the same pattern as inc-4's weights and #34's thresholds — chosen ahead of data, calibrate-on-use.
- *Alternative:* keep the thresholds tunable method-defaults with plain, conservative starting values (D-ANL.6) — a too-high threshold simply surfaces fewer insights (fail-quiet, never fail-loud-with-noise), which is the safe direction for a low-confidence feature. Widen as real use reveals what "chronic" means for this user. The over-fit risk is bounded by the honest-empty floor (an insight with no signal stays silent rather than firing on a bad threshold).

**RF #4 — the completion-vs-intake insight could read as a guilt-meter, not a help.**
- *Disagreement:* "you've added eleven and finished three" can land as a productivity scold for an ADHD/overwhelm-prone user — the opposite of the meet-them-where-they-are intent (and directly counter to Luke's own stated context).
- *Evidence:* the architecture §6 + the prime directive frame the WMS as anxiety-REDUCING, not performance-tracking; a naive balance metric inverts that.
- *Alternative:* phrase the balance insight as an ORIENTING signal, not a judgment ("you're capturing faster than finishing — might be worth closing a few out" vs "you only finished three") — the plain-language phrasing is the builder's call but the NON-judgmental framing is a named constraint (it composes the abstraction-first / non-tech-trust discipline). If the right phrasing proves to inevitably read as a scold, insight #3 is the first to cut (it's the weakest of the three) — named so the build doesn't ship a guilt-meter to satisfy an AC.

**RF #5 — this is the LAST increment; is the WMS actually done after it?**
- *Disagreement/scope honesty:* sealing analytics closes the 7-increment roadmap, but several named follow-ons remain OUT (the #71 edge-mutating self-heal; widening the #34 seed taxonomy so `work-tracking` is first-class; registering Money/Personal-Home as FBM projects to upgrade those lenses from cadence- to STATE-derived; the behavioural auto-learn of the lens choice). A reader could mistake "last increment sealed" for "WMS complete."
- *Evidence:* architecture §5 (the FBM ground-truth gap), §8/inc-6 (the taxonomy-widening follow-on), inc-4 RF#2 / #71 (the self-heal seam).
- *Alternative:* the §9 bookkeeping records that the increment ROADMAP is complete while the named follow-ons remain explicitly open (they are post-roadmap enhancements, not roadmap increments) — so "roadmap done" is honest and "WMS perfect" is not claimed.
