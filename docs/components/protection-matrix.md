# protection-matrix

## What it does

`protection-matrix` is the component that makes loam's protection
pillar machine-checkable. It pairs a living catalogue of every known
way an AI betrays a user by default with the `loam guards` verb that
checks loam's actual guard coverage against that catalogue and names
the gaps.

Two pieces make up the component:

- **The catalogue** — `data/failure-mode-guard-matrix.yaml` is the
  single source of truth: every known failure mode × loam's actual
  guard × is-it-default-on? × floor-vs-proportional × how we verify
  the guard fires.
- **The `loam guards` coverage-check** — derives the live guard set
  from ground truth (the actual hooks, gates, and settings in the
  tree), reconciles it against the catalogue, and reports where a
  catalogued failure mode has no live guard, or a live guard isn't
  catalogued. It is a reporter, not a gate — it always exits 0 so it
  never blocks a workflow; the report is the value.

## How to invoke

The user-facing CLI verb:

```bash
loam guards                       # coverage report: catalogue vs the live guard set
loam guards --refresh             # also regenerate the human-readable companion doc
loam guards --out <path>          # write the refreshed companion to a named path
loam guards --catalogue <path>    # check against a catalogue other than the default
loam guards --repo-root <path>    # override the auto-detected loam repo root
```

## Observable surface

What you can `cat` / `grep` to see the component working:

- **The catalogue.** `framework/protection-matrix/data/failure-mode-guard-matrix.yaml`
  — the version-controlled matrix every coverage report reconciles
  against.
- **The coverage report.** `loam guards` prints a
  "protection-pillar coverage report" naming covered modes and gaps;
  `--refresh` writes a generated human-readable companion doc (marked
  `GENERATED by loam guards --refresh` so it is never hand-edited).
- **The live guard set.** The report derives live guards from ground
  truth — the PreToolUse safety hooks, release gates, and settings
  actually present in the tree — so a report is only as current as the
  tree it ran against.

## Stable surfaces (for plugin authors)

A plugin that adds a guard (a new PreToolUse hook, a new gate) makes
that guard visible to `loam guards` by cataloguing it in the matrix
with its failure mode, default-on status, and verification method. An
uncatalogued live guard surfaces in the report as a reconciliation
gap, prompting the catalogue entry.
