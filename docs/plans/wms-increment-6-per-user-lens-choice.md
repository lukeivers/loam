## §1 Summary / TL;DR

Increment 6 is the **L4 wiring** — the mechanism that decides WHICH lens(es) a given user sees by default per-turn, derived from their #34 profile, owner-settable, with a plain-language switch path. **It builds NO new lens.** Increment 5 re-bundled goals/plate/waiting-on, so the lens SET is complete; this increment is the chooser over that set.

Three pieces, all on `primary-persona`, all composing built primitives (Lens 1):

1. **A lens-choice resolver** (`keep_pace/lens_choice.py`) — a deterministic, fail-open function that reads the user's #34 profile (the `work-tracking` area, a `preferred-lens` axis) and resolves the set of lens(es) that surface by DEFAULT per-turn for this user. Mirrors `intake.py`'s `work-tracking` read precedent EXACTLY: `cell_or_prior` read, openness-prior default when the cell is absent, never raises. A non-tech / simplest-actionable profile → `on-my-plate`; a projects-oriented profile → `projects`; a streams/broad profile → `work-streams` (the architecture's openness default); a power user can pick/override. The resolver returns a SET (the chosen lens(es)), not a single name — multi-select is expressible.

2. **The per-turn surface reconciliation** (`session_start_emitter.py` registration, made choice-aware) — today the M-FBM branch unconditionally registers `work-streams` + `projects` + `relational` at `TriggerKind.turn` (three always-on blocks every turn for every user). Increment 6 makes that registration RESPECT the resolver: register the CHOSEN lens(es) as the per-turn surface; keep the others available as the inc-5 on-demand `render_*_block` entry points. This is the brief's central reconciliation and the F2-named replace-vs-add tension (§3 D-WMS6.3 / §10 RF #1). It composes with the FBM-load-filter / don't-bloat discipline: the whole point is LESS per-turn surface (the right lens, not all of them).

3. **The switch / override path** (`keep_pace/lens_choice.py` writer + a plain-language ask handler) — how a user changes their lens. A plain-language ask ("just show me what's on my plate" / "I think in projects") is the switch; it owner-gated-writes the `work-tracking` / `preferred-lens` cell so the next turn surfaces the new choice. **Critical constraint surfaced (§3 D-WMS6.4 / §10 RF #2):** `interaction_model.apply_override` REJECTS any area not in `AIM_AREAS` (line 694), and `work-tracking` is NOT in `AIM_AREAS` — so the switch CANNOT round-trip through `apply_override` today. The writer is a WMS-area-scoped persistence path that writes the same matrix line-shape (reusing `render_matrix` / the `Cell` line format) WITHOUT widening the seed-writer taxonomy — exactly the fence the brief draws (consume #34 read-only; do not edit the #34 INTERACTION-MODEL component or the workspace-bootstrap seed-writer).

**AC families:** AC.CHOICE.* (the resolver: profile → default lens-set, fail-open) · AC.SURFACE.* (the per-turn surface respects the choice; the un-chosen lenses stay on-demand; zero bloat over the choice) · AC.SWITCH.* (the plain-language switch changes the surfaced lens for the next turn, owner-gated, no #34-taxonomy mutation) · AC.WMS6.LIVE.1 (the outcome-altitude — a real user with a given #34 profile gets the right lens surfaced live with NO pre-arranged state, and a switch changes it).

**Key decisions baked:** the choice is a #34 `work-tracking`/`preferred-lens` cell read read-only via the intake precedent (D-WMS6.1); the resolver is DETERMINISTIC + fail-open to the openness default, no LLM on the hot path (D-WMS6.2, mirrors `classify_area`); ★ choosing a lens REPLACES the always-on inc-4 default-set rather than adding (D-WMS6.3 — the per-turn-bloat fork); ★ the switch writer is a WMS-area-scoped path that does NOT widen the seed-writer taxonomy or `apply_override`'s area gate (D-WMS6.4); ★ the DEFAULT lens per tech-level (D-WMS6.5, the genuine product-shape call); the switch is autonomous-write-after-plain-confirm, not a separate gate (D-WMS6.6).

**F2 scope realism:** this is a SINGLE-component increment on a sealed component, composing two built read-only primitives (the five lenses + the #34 read engine) with a proven consumption precedent (intake's `work-tracking` read) to mirror. The build SURFACE is small (one resolver module + one writer + a registration change). The genuine risks are NOT build-size — they are (a) accidentally widening the #34 taxonomy or `apply_override`'s gate to make the switch writable (the fence breach, RF #2), and (b) shipping a default that surfaces NOTHING for an un-seeded user (a regression from inc-4's always-on blocks — the resolver MUST fail-open to a sensible default, RF #3). Both are named as halt-class so the build cannot drift into them silently.

## §3 Named decisions (with recommendations) — surface to Luke

Every decision carries a recommendation. ★ marks a genuine product-shape call worth Luke's deliberate eyeball; the rest are autonomous method-calls (the architecture + the existing precedent already rule the shape — recorded, not gated).

### D-WMS6.1 — Where the lens choice lives. **RECOMMEND (autonomous method-call): the choice is a #34 cell — the `work-tracking` area + a new `preferred-lens` axis — read READ-ONLY via the SAME `cell_or_prior` path `intake.py` already uses for `work-tracking`/`intake-aggressiveness`.** The architecture (WMS-D3 §9) already rules this: "lens choice is per-user → a `work-tracking` area in #34 with a preferred-lens axis." Intake (inc-3) established the precedent: it reads a `work-tracking` cell that the seed-writer does NOT emit, degrading cleanly via `cell_or_prior`'s openness prior. Inc-6 mirrors it exactly. No new store; reuses the sealed #34 read engine (Lens 1).

### D-WMS6.2 — The resolver is deterministic + fail-open, no LLM on the hot path. **RECOMMEND (autonomous method-call): a deterministic map from the `preferred-lens` cell value → the default lens-set, fail-open to the openness default when the cell is absent/garbled — NO model call on the per-turn path.** Mirrors `interaction_model.classify_area` (the design §4b "no model-decides-each-turn; the hook fires every turn and must fail-open"). The per-turn surface registration runs every turn; it must be cheap + never wedge the turn. The choice is a cell LOOKUP, not an inference.

### D-WMS6.3 — ★ Choosing a lens REPLACES the always-on default-set, or ADDS to it. **RECOMMEND: REPLACE — the chosen lens(es) BECOME the per-turn surface; the un-chosen lenses move to the inc-5 on-demand `render_*_block` entry points (rendered when asked).** This is ★ because it is the brief's explicitly-named replace-vs-add fork and a genuine product call. The case for REPLACE (my recommendation): the whole point of the increment, stated in the brief and the architecture §6, is LESS per-turn surface — "surface the chosen lens(es), keep the others on-demand," composing the FBM-load-filter / don't-bloat discipline. Today three always-on blocks fire every turn for every user; that is the bloat L4 exists to fix. The case for ADD (the alternative, surfaced honestly): a power user might want several lenses always-on, and REPLACE risks HIDING a lens a user relied on. **The resolution that captures both:** REPLACE is the default behaviour, but the resolver returns a SET, so a power-user profile can choose MULTIPLE lenses always-on (the "add" case becomes "choose a larger set") and the openness default (an un-seeded user) resolves to a SENSIBLE default-set, NOT zero blocks (RF #3 — never surface nothing). So REPLACE-with-a-multi-select-set subsumes ADD without a separate code path. **My recommendation: REPLACE, default-set ≠ empty, multi-select expressible.** Surfaced because "does picking a lens hide the others by default" is Luke's product call to set.

### D-WMS6.4 — ★ The switch writer does NOT widen the #34 taxonomy or `apply_override`'s area gate. **RECOMMEND: persist the `work-tracking`/`preferred-lens` cell via a WMS-area-scoped writer that re-emits the matrix in the seed-writer's line-shape (reusing `interaction_model.render_matrix` + the `Cell` format) — WITHOUT adding `work-tracking` to `AIM_AREAS` and WITHOUT changing `apply_override`'s `if area not in AIM_AREAS` rejection.** This is ★ because it is a real architectural fork forced by a verified constraint: `apply_override` (interaction_model.py line 694) REJECTS any area not in `AIM_AREAS`, and `work-tracking` is NOT in `AIM_AREAS` — so the switch CANNOT round-trip through the existing override writer. Two paths exist: (a) **WMS-scoped writer** (my recommendation) — inc-6 writes the cell itself, in the same line-shape, fence-respecting, no edit to the sealed #34 gate or the workspace-bootstrap seed-writer; or (b) **widen `AIM_AREAS` + the seed taxonomy** to make `work-tracking` a first-class #34 area so `apply_override` accepts it — which is a `interaction_model.py` change AND a `workspace-bootstrap` seed-writer change (two sealed components, the explicit fence breach the brief forbids). **My recommendation: (a)**, because the brief says consume #34 read-only and not edit the INTERACTION-MODEL component; the writer reuses #34's line-shape WITHOUT mutating its taxonomy. **If Luke prefers the long-term-cleaner path (his stated default), (b) is the cleaner end-state** — `work-tracking` as a real #34 area that `apply_override` writes uniformly — but it is a SEPARATE workspace-bootstrap + interaction-model cycle, out of THIS fence; I name it as the clean follow-on, and the build HALTS rather than reaching into those sealed components (§8 #2). Surfaced because "fence-respecting WMS writer now vs taxonomy-widening cleaner-later" is the genuine architectural fork.

### D-WMS6.5 — ★ The DEFAULT lens per tech-level. **RECOMMEND: the openness default (an un-seeded user, OR `technical-exposure: plain`) → `on-my-plate` (the simplest actionable view); a projects-oriented profile → `projects`; a broad/power profile (`technical-exposure: deep` or an explicit pick) → the user's chosen set, openness-defaulting to `work-streams` (the architecture's "broadest" default) for an engaged-but-unspecified user.** This is ★ because it is the genuine product-shape call the brief flags: it defines what the RIGHT lens IS for each kind of user. The tension worth Luke's eyeball: the architecture §1/WMS-D3 names `work-streams` as the openness default (the broadest lens); but the brief and §6 say "a non-tech user gets the simplest actionable view, e.g. on-my-plate." These pull different ways — broadest-for-engagement vs simplest-for-a-lost-user. **My resolution (recommended):** map it to the EXISTING `technical-exposure` axis the #34 matrix already carries (no new signal needed) — `plain` exposure (the non-tech / meet-them-simply user) → `on-my-plate` (simplest actionable); `open` exposure (the engaged default) → `work-streams` (broadest, the architecture's openness default); `deep` exposure → the user's explicit pick or a multi-lens set. This composes the #34 self-recovery rule (§6 point 5 of the architecture: a lost user's distress dials the lens to the simplest — `on-my-plate`, one thing). Surfaced because "what lens does a brand-new non-tech user see on turn one" is Luke's to set, and the on-my-plate-vs-work-streams default is the load-bearing choice.

### D-WMS6.6 — The switch is autonomous-write-after-plain-confirm, not a separate owner gate. **RECOMMEND (autonomous method-call): a plain-language switch ("just show me my plate") is treated as an explicit user statement — the persona confirms in plain language ("Okay — I'll lead with what's on your plate from now on") and writes the cell; it does NOT open a separate ratification gate.** The #34 model already treats an explicit user statement as the highest-confidence, classifier-free signal that hard-sets a cell (interaction_model.py D-N4.3 / the override path). A lens switch is exactly that class of statement. The write is owner-INITIATED (the user asked), so it needs no second gate — the plain confirm IS the verify-before-write step (the prime-directive operating loop). This stays inside the #34 MVP fence (cells move only by explicit statement). The autonomy floor is unaffected: changing which lens you SEE is a talking/exposure preference, never a consequence-bearing action.

## §6 Acceptance criteria (outcome-shape; method-in-AC test passed on each)

Each AC states an observable OUTCOME; the method that satisfies it is the builder's call. The method-in-AC test (can the AC be satisfied by a method other than the one I have in mind?) passes on each.

**AC.CHOICE — the lens-choice resolver**
- **AC.CHOICE.1** — Given a #34 matrix carrying a `work-tracking`/`preferred-lens` cell with a recognised value, the resolver returns the lens-set that value maps to (a projects-preference → the projects lens; a plate-preference → on-my-plate; a streams/broad-preference → work-streams). (Outcome: the profile's stated preference picks the lens-set. The cell-read mechanism + the value→set map are the builder's call.)
- **AC.CHOICE.2** — Given a #34 matrix with NO `work-tracking`/`preferred-lens` cell (an un-seeded or fresh user), the resolver returns a non-empty SENSIBLE default lens-set derived from the existing `technical-exposure` cell per D-WMS6.5 (plain → on-my-plate; open → work-streams) — NEVER an empty set, NEVER nothing surfaced. (The fail-open-to-a-real-default outcome — the anti-regression guard; RF #3.)
- **AC.CHOICE.3** — Any matrix error (missing file, unreadable, malformed cell) degrades the resolver to the openness default lens-set without raising — the per-turn surface proceeds exactly as a fail-open turn does. (Fail-open, mirroring `load_interaction_model`'s contract. The resolver NEVER wedges the turn.)
- **AC.CHOICE.4** — The resolver makes NO model/LLM call and performs NO store mutation on the per-turn path — it is a deterministic read over the #34 cell + the work-item read the chosen lens already does. (The hot-path-cheap, no-side-effect outcome — D-WMS6.2.)

**AC.SURFACE — the per-turn surface respects the choice**
- **AC.SURFACE.1** — Given a resolved lens-set, the per-turn surface registers exactly the CHOSEN lens(es) as the turn blocks; a lens NOT in the resolved set is NOT registered as a `TriggerKind.turn` contributor for that user. (Outcome: the turn surface = the chosen set. The registration mechanism is the builder's call.)
- **AC.SURFACE.2** — An un-chosen lens remains available on demand: its inc-5/inc-2/inc-4 `render_*_block` entry point still renders the correct view when invoked, even though it is not a per-turn block. (The replace-not-delete outcome — choosing a lens hides it from the per-turn surface, never removes its capability; D-WMS6.3.)
- **AC.SURFACE.3** — For a given resolved set, the per-turn block COUNT is the size of the chosen set — it does NOT pile all lenses on every turn. A single-lens choice yields one WMS lens block where today three always-on blocks fire. (The anti-bloat outcome — the FBM-load-filter / don't-bloat composition; the measurable "less per-turn surface" the increment exists to deliver.)
- **AC.SURFACE.4** — A resolver/registration error fails OPEN to the current always-on default-set (work-streams + projects + relational), NOT to zero blocks — the choice-aware path never regresses a user to a blank surface. (The fail-open-to-the-old-default guard — the anti-regression outcome; §8 #3.)

**AC.SWITCH — the plain-language switch / override path**
- **AC.SWITCH.1** — A plain-language switch ("just show me what's on my plate" / "I think in projects") persists the user's `work-tracking`/`preferred-lens` choice such that the NEXT turn's resolver returns the switched-to lens-set. (Outcome: the switch changes what surfaces next turn. The persistence mechanism is the builder's call.)
- **AC.SWITCH.2** — The switch write does NOT mutate the #34 taxonomy: `AIM_AREAS` is unchanged, `apply_override`'s area-gate is unchanged, and the workspace-bootstrap seed-writer is untouched — the cell is persisted in the existing matrix line-shape without widening any sealed taxonomy. (The fence-respecting-write outcome — D-WMS6.4 / §5. Verifiable: the written matrix round-trips through the live `load_interaction_model` reader, and no diff lands in `interaction_model.AIM_AREAS` / `apply_override` / the seed-writer.)
- **AC.SWITCH.3** — The switch confirmation to the user carries zero internal vocabulary: no axis names, no cell values, no slugs, no paths, no enums — a plain-language acknowledgement of the new framing ("Okay — I'll lead with what's on your plate"). (The zero-internal-vocab HARD invariant on the switch surface; mirrors the #34 inspect/inject plain-by-construction discipline.)
- **AC.SWITCH.4** — An overridden lens cell is honoured over the technical-exposure-derived default: once a user explicitly picks a lens, the resolver returns the picked set even when the exposure-derived default would differ (the explicit-statement-wins precedence, mirroring #34's `locked`/`high`-confidence override). (The stated-preference-is-sticky outcome.)

**AC.WMS6.LIVE — the outcome-altitude AC** (`outcome-altitude: true`)
- **AC.WMS6.LIVE.1** — Against a REAL #34 matrix file (an isolated fixture home) carrying a REAL `technical-exposure`/`preferred-lens` profile, and a REAL work-item store with no pre-arranged lens/registration state: (a) the live resolver + the live per-turn registration path surface the RIGHT lens for that profile (a `plain`/plate profile surfaces the on-my-plate block and NOT the streams/projects/relational always-on trio; a projects profile surfaces the projects block); (b) invoking the live switch path with a plain-language preference change WRITES the cell such that a fresh live resolve returns the switched-to lens-set; (c) the un-chosen lenses' live `render_*_block` entry points still render correctly on demand. Exercised through the real production entry points (the resolver, the registration assembly, the switch writer), no mocks at the #34-file or store boundary, no pre-seeded registration. (The brief's named outcome-altitude: a real user with a given #34 profile → the right lens surfaces by default live, and a switch changes it, no pre-arranged state.)

## §7 Build steps (method-level guidance only — builder's call per ODD §1.1)

1. **Manifest** at `docs/plans/wms-increment-6-per-user-lens-choice.manifest.yaml` (paired below). BASELINE = `build/wms-increment-5` tip @ build time. Single component: `primary-persona`, `new_component: false`.

## §8 Halt triggers (abort the in-flight build + surface)

1. **No lenses to choose among.** If BASELINE resolves to a tree without the five lenses + the #34 read engine (e.g. an accidental main-based build), HALT — there is nothing to choose among. (The §11 predecessor check is the pre-build guard.)
2. **A needed #34-taxonomy change.** If the switch writer cannot persist the `work-tracking`/`preferred-lens` cell WITHOUT adding `work-tracking` to `AIM_AREAS`, changing `apply_override`'s area-gate, or editing the workspace-bootstrap seed-writer, HALT and surface — that is a SEPARATE workspace-bootstrap + interaction-model cycle (the D-WMS6.4 path (b)), NOT this increment. Do NOT reach into those sealed taxonomy surfaces.
3. **Fail-open-to-empty regression.** If the resolver's fail-open path would surface ZERO turn blocks for an un-seeded user (a regression from inc-4's always-on blocks), HALT — the default lens-set MUST be non-empty (AC.CHOICE.2 / AC.SURFACE.4). A user must never lose their per-turn surface because the choice machinery degraded.
4. **A needed store-side change.** If the resolver or a chosen lens needs a query the runtime doesn't expose, a projection field that doesn't exist, or any store MUTATION, HALT and surface — do NOT open a sealed objective-tracker amendment inside this increment.
5. **Surrounding ODD violation.** If the build discovers an ODD violation in the surrounding inc-1..inc-5 code (unnamed-case code, a method-in-AC), surface it — do NOT silently extend it (the subagent-ODD-halt discipline).
6. **Per-turn surface widening, not narrowing.** If the choice-aware registration ends up registering MORE blocks than the chosen set (e.g. choosing on-my-plate but still registering the trio), HALT — the increment's whole point is LESS per-turn surface (AC.SURFACE.3); a build that adds rather than replaces has inverted the objective.

## §10 F2 Ruthless Feedback (honest doubts + named design risks)

**RF #1 — the replace-vs-add per-turn-blocks tension (the brief's named tension).**
- *Disagreement/tension:* choosing a lens could REPLACE the inc-4 always-on default-set (the chosen lens becomes the surface, others go on-demand) OR ADD to it (the chosen lens joins the always-on trio). Replace risks hiding a lens a user relied on; add re-bloats the surface the increment exists to slim.
- *Evidence:* `session_start_emitter.py`'s M-FBM branch registers `work-streams` + `projects` + `relational` unconditionally at `TriggerKind.turn` today (three always-on blocks every turn, every user). The architecture §6 + the brief both say the point is LESS surface ("the right lens, not all of them").
- *Alternative + resolution:* REPLACE as the default, but the resolver returns a SET so a power user expresses "add" as "choose a larger set," and the un-seeded default-set is non-empty (RF #3). REPLACE-with-multi-select subsumes ADD without a second code path. Recommended (D-WMS6.3), surfaced because the replace-hides-others default is Luke's product call.

**RF #2 — the #34-taxonomy fence breach trap (the verified constraint).**
- *Disagreement:* the obvious "use `apply_override` to write the lens choice" instinct FAILS — `apply_override` (interaction_model.py line 694) rejects any area not in `AIM_AREAS`, and `work-tracking` is NOT in `AIM_AREAS`. A build that "fixes" this by adding `work-tracking` to `AIM_AREAS` or editing the seed-writer breaches the fence the brief draws (consume #34 read-only; don't edit the INTERACTION-MODEL component).
- *Evidence:* `interaction_model.AIM_AREAS` (6 areas, no `work-tracking`); `apply_override` line 694 `if area not in AIM_AREAS: return ok=False`; `intake.py` reads `work-tracking` via `cell_or_prior` (the openness-prior path) and NEVER writes it through `apply_override`.
- *Alternative:* a WMS-area-scoped writer that re-emits the matrix line-shape (reusing `render_matrix` + `Cell`) without widening any taxonomy (D-WMS6.4 path (a), recommended). Named as a halt trigger (§8 #2) so the build cannot drift into the taxonomy edit silently. The cleaner long-term end-state — `work-tracking` as a real #34 area — is a named SEPARATE follow-on, not this fence.

**RF #3 — the fail-open-to-empty regression risk.**
- *Disagreement:* a naive resolver that returns "the chosen lens-set" and surfaces nothing when the cell is absent would REGRESS every un-seeded user from inc-4's always-on blocks to a BLANK per-turn surface — strictly worse than today.
- *Evidence:* today the M-FBM branch registers the trio unconditionally (every user, seeded or not, gets a per-turn surface). A choice-aware path that defaults to empty silently removes that.
- *Alternative:* the resolver fails open to a NON-EMPTY default lens-set derived from `technical-exposure` (AC.CHOICE.2/.3, D-WMS6.5) and the registration fails open to the current always-on default-set on any error (AC.SURFACE.4) — a user NEVER loses their surface. Named as a halt trigger (§8 #3).

**RF #4 — the architecture re-bundling carry-through (scope honesty).**
- *Disagreement:* the architecture §7 originally placed on-my-plate + waiting-on lens-BUILDS in increment 6; inc-5 re-bundled them, re-scoping increment 6 to lens-CHOICE only. A reader of the architecture row-6 ("per-user lens choice") + the §3 lens-table ("on-my-plate / waiting-on: Increment 6") sees an inconsistency.
- *Evidence:* architecture §7 row-6 = "per-user lens choice (L4 wiring)"; §3 lens-table lists on-my-plate + waiting-on as "Increment 6"; inc-5's plan §9/RF#4 already recorded the re-bundling.
- *Alternative:* this plan carries the re-scope forward explicitly (increment 6 = CHOICE only, lenses already shipped) and the §9 bookkeeping reconciles the architecture row + lens-table on seal so the roadmap stays honest. Named, not silently absorbed.

**RF #5 — the `preferred-lens` value vocabulary is unproven (am I over-fitting the map?).**
- *Disagreement with my own design:* the resolver maps a `preferred-lens` cell value → a lens-set, but no user has ever set this cell (the axis doesn't exist in the seed taxonomy yet). The value vocabulary (which strings map to which lens) is a guess until real switches populate it.
- *Evidence:* `intake.py`'s sibling `intake-aggressiveness` axis has a fixed `_VALID_AGGR` vocabulary (off/light/eager) that was similarly chosen ahead of real data; it works because the values are few + plain.
- *Alternative:* keep the `preferred-lens` vocabulary SMALL + plain (the lens names: plate / projects / streams / goals / waiting-on, plus a "simplest" alias) and DERIVE the default from the existing `technical-exposure` axis (D-WMS6.5) rather than inventing a rich new vocabulary — so an un-set or unrecognised value degrades to the exposure-derived default, never to nothing (AC.CHOICE.2). The vocabulary is calibrate-on-use (the same Lens-4 discipline as #34's thresholds + inc-4's weights): start small, widen as real switches reveal the values users actually say. Recommended; the over-fit risk is bounded by the fail-open-to-exposure-default floor.
