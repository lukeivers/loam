## §1 Summary / TL;DR

**What ships.** A settings-fragment auto-composer wired into `pos-sync` (`workspace_sync.cli`): after a sync successfully advances `<workspace>/framework/`, the composer DISCOVERS every loam component's `settings.fragment.json` under the synced `<workspace>/framework/` tree, and COMPOSES their `hooks` blocks into `<workspace>/.claude/settings.json` — **additively** (only ADD loam-owned hook entries), **idempotently** (a re-run never duplicates), and **non-destructively** (the user's / workspace's own hook entries and every other settings key are never modified or removed). Each composed entry is tagged loam-owned so the composer has a clean ownership boundary: it OWNS exactly the entries it wrote, can refresh/remove a previously-composed fragment that has since disappeared, and NEVER touches a user-authored entry. `${LOAM_REPO}` in each fragment command is resolved to the workspace's framework root at compose time. The composer runs automatically on a successful sync (given the non-clobber guarantee), prints a one-line summary of what was added/refreshed/removed, and supports a `--dry-run` view that reports the would-add/would-remove plan and writes NOTHING. This is the piece that turns the frame-kernel + keep-pace fragments from hand-merged-on-a-gated-step into auto-wired-on-sync.

**Why this closes RF-1 (the whole point).** frame-kernel 1a/1b and keep-pace each ship a PORTABLE `settings.fragment.json` but defer the live wiring to a "GATED hand-merge step the dispatcher times" — because **workspace-sync did not auto-compose fragments** (1b §7-5 / §10-RF-1 verbatim). That means scale-free governance was a portable artefact, not live behaviour: every fragment-shipping component had to be hand-merged into each workspace's `settings.json`. This composer makes the fragment the SOURCE OF TRUTH and the live wiring a derived, idempotent, non-clobbering output of sync.

**AC families.** `AC.SFC.*` (Settings-Fragment-Composer) — discovery (the glob that finds component fragments at their differing depths) + additive/idempotent merge keyed by a loam-ownership tag + the non-clobber guarantee (user entries + non-hook keys untouched) + `${LOAM_REPO}` resolution + automatic-on-sync with a surfaced summary + `--dry-run` non-destructive view + the outcome-altitude real-sync probe.

**Key decisions baked (recommendations in §3; all autonomous, none owner-gated).** (1) **Merge strategy** — append component-fragment hook entries into `settings.json` keyed by event, each tagged loam-owned; dedupe key = the loam-ownership tag carrying the source-fragment identity + the command string, so a re-run detect-and-skips an already-present block (D-SFC.1). (2) **Non-clobber** — the composer reads/writes ONLY entries carrying its ownership tag; user/workspace entries (untagged) and every non-`hooks` key are structurally out of the composer's write set; removal is limited to a previously-composed entry whose source fragment is gone (D-SFC.2). (3) **Discovery** — glob `<workspace>/framework/*/hooks/**/settings.fragment.json` (catches frame-kernel at `hooks/` depth AND keep_pace at `hooks/keep_pace/` depth, verified); a component opts a fragment in simply by shipping that file (D-SFC.3). (4) **When** — automatic on a successful sync, with a one-line surfaced summary; `--dry-run`/`--no-compose` available (D-SFC.4). (5) **Backout/safety** — `--dry-run` reports the plan and writes nothing; every real write is additive + idempotent + tag-scoped; a malformed/unreadable `settings.json` HALTS the compose step (never a destructive overwrite) while the sync itself stands (D-SFC.5).

**F2 RF on scope realism (full §10).** The natural shape EXTENDS the sealed `workspace-sync` component (a new composer module + a wire-in at the end of `_execute_sync` + a CLI flag + tests). **The load-bearing RF (RF-1 below): the composer deliberately writes `<workspace>/.claude/settings.json`, which is OUTSIDE the D-migration HC#6 fence (`pos-sync` operates exclusively inside `<workspace>/framework/`).** This is a real, named widening of pos-sync's write surface — surfaced, not silent — with the safety envelope (additive + tag-scoped + idempotent + dry-run) sized to the blast radius (every workspace's settings.json). The activation against Luke's LIVE workspace is NOT part of this build (fixture-tested only; live activation is the same owner-gated step 1a/1b §7 left open).

## §3 Halt-and-surface BEFORE build (named decisions, recorded + recommended)

All decisions below are **autonomous** (method-level, in-scope per the dispatch). Each carries a recommendation; none is owner-gated. Recorded here so the builder does not re-derive.

**FEASIBILITY (resolved at plan-authoring — CONFIRMED, with a named caveat; Tier-0 from the source).** *Can `workspace-sync` compose `<workspace>/.claude/settings.json`?* **YES — feasibly, but it requires a DELIBERATE reach OUTSIDE the current HC#6 write fence, which this plan names explicitly (RF-1).** Tier-0 evidence: (a) `pos-sync` today does NOT touch `.claude/settings.json` at all — `grep` across `framework/workspace-sync/src/` returns zero `settings.json` writes; the D.3 CLI's structural promise (`cli.py` module docstring, HC#6) is "every git operation runs with `-C <workspace>/framework`; files outside `framework/` are structurally unreachable." (b) `<workspace>/.claude/settings.json` lives at the workspace ROOT, OUTSIDE both `framework/` and the `workspace/` state subdir (`workspace_paths.py:113` — "`.claude/` lives at workspace root per D-Q.A4 lock"). (c) The composer is therefore a NEW write surface, run as a post-merge Python step (NOT a git operation inside `framework/`) — it does not violate HC#6's GIT promise (the merge still happens only in `framework/`), but it DOES extend pos-sync's total write surface to the workspace-root `.claude/`. **This is feasible and `workspace-sync` IS the right owner** (the composer's input is "what fragments did this sync land" — a sync-lifecycle fact only the sync step knows). The widening is real and named (RF-1); the non-clobber + idempotent + dry-run envelope is sized to it. **No HALT: the safety can be guaranteed** (see D-SFC.1/.2/.5) and workspace-sync IS the correct home — if either were false this plan would HALT per the dispatch.

**D-SFC.0 — Fence: EXTEND `workspace-sync`.** *Recommendation:* extend the sealed `workspace-sync` component (rationale §2). Manifest names `workspace-sync`, `frozen_baseline: false`, `extra_allowed_prefixes: [framework/workspace-sync/]`. No new component; no other sealed fence widened (`workspace-bootstrap`'s `claude_dir` + the two fragments are IMPORTED/READ, never edited — §8 halt-trigger #3 guards this).

**D-SFC.1 — Merge strategy + dedupe key (idempotency).** *Recommendation:* compose by APPENDING, into `settings.json["hooks"][<event>]`, each matcher-group from a discovered fragment, with every composed matcher-group carrying a **loam-ownership tag** — a stable marker the composer writes and reads back. The **dedupe key** = (source-fragment identity + the resolved command string(s) in the group). On each sync the composer computes the desired loam-owned set from the discovered fragments, compares against the loam-owned set already present in `settings.json` (matched by the tag + key), and writes the difference: ADD missing, leave present-and-identical untouched (the idempotency guarantee — a second sync with no fragment change is a no-op write or no write at all), and REFRESH an entry whose resolved command changed (e.g. `${LOAM_REPO}` now resolves differently). Recommended tag shape: a reserved key on the matcher-group object (e.g. a `"_loam"` metadata field naming the source fragment's component + relative path) OR, if Claude Code rejects unknown keys on a matcher-group, a sentinel inside the group keyed off the command path prefix (`<framework_root>/...` under the synced tree) — the builder picks whichever the live `settings.json` schema accepts (the SHAPE is pinned: every composed group is unambiguously identifiable as loam-owned + traceable to its source fragment; the exact tag field is the build-time-empirical knob, verified by AC.SFC.2 + AC.SFC.5's idempotency assertion). Rationale: a content-hash-only dedupe can't distinguish a loam entry the user later hand-edited from a user entry — the ownership tag gives a CLEAN boundary (D-SFC.2 depends on it).

**D-SFC.2 — Non-clobber guarantee (the safety keystone).** *Recommendation:* the composer's write set is STRUCTURALLY limited to loam-owned entries. Concretely: (a) it NEVER modifies or removes any matcher-group that lacks the loam-ownership tag — user/workspace hook entries are invisible to its write path (read-only context at most); (b) it NEVER touches any settings key other than `hooks` (`statusLine`, `permissions`, `env`, `model`, every other top-level key is copied through verbatim); (c) within `hooks`, for an event that has BOTH user-owned and loam-owned groups (e.g. a user `Stop` hook beside a loam-composed `SubagentStop`), the user groups are preserved in place and loam groups are reconciled around them; (d) the ONLY removal the composer performs is deleting a previously-composed loam-owned entry whose source fragment no longer exists in the synced tree (clean ownership: loam removes only what loam added and no longer ships). Verified against the LIVE settings shape: the current `<workspace>/.claude/settings.json` carries `statusLine` + a user `Stop` hook — AC.SFC.3 asserts BOTH survive a compose untouched. Rationale: this is the highest-blast-radius guarantee (every workspace's settings.json); a tag-scoped write set is the structural (not behavioural) enforcement of non-clobber.

**D-SFC.3 — Discovery glob + opt-in.** *Recommendation:* discover fragments with `<workspace>/framework/*/hooks/**/settings.fragment.json` (recursive under each component's `hooks/`). Verified Tier-0: this glob catches BOTH shipped fragments at their differing depths — `frame-kernel/hooks/settings.fragment.json` AND `hands-off-lifecycle/hooks/keep_pace/settings.fragment.json`. A component opts a fragment in by SHIPPING that file under its `hooks/` tree — no registry, no manifest entry (Lens 1: the fragment's mere presence is the opt-in; the composer is the first consumer of `settings.fragment.json` as a discoverable surface, confirmed by grep — nothing else globs it today). The composer reads each fragment's `hooks` block (ignoring the `_comment` field the fragments carry) and composes it. Rationale: presence-as-opt-in keeps fragment-shipping zero-ceremony for component authors — the exact property that makes governance scale-free.

**D-SFC.4 — When it runs: automatic-on-successful-sync, with a surfaced summary.** *Recommendation:* run the composer automatically at the end of every sync that advanced or confirmed `<workspace>/framework/` (the FF, plain-merge, LLM-resolved, AND up-to-date paths — so a re-sync that lands no new framework commits still reconciles settings if a fragment set drifted), AND print a one-line summary to stderr naming what was added/refreshed/removed (e.g. `[settings-composer] +2 loam hook entries (frame-kernel SubagentStart, SubagentStop); 0 removed; 0 user entries touched`). Automatic is safe BECAUSE of the non-clobber guarantee (D-SFC.2) — there is no destructive path to gate behind a flag. Provide `--no-compose` (skip the step entirely) and `--dry-run-compose` (D-SFC.5) as the opt-out / preview surfaces. Rationale: the dispatch recommends automatic-on-sync given non-clobber; the surfaced summary keeps the action VISIBLE (loam doctrine: expose the substance) so the operator always sees what wired up.

**D-SFC.5 — Backout / safety: dry-run + never-destructive.** *Recommendation:* `--dry-run-compose` computes and PRINTS the full would-add / would-refresh / would-remove plan (per entry: event, source fragment, the loam-ownership tag, resolved command) and writes NOTHING. Every REAL write is: additive (D-SFC.1), tag-scoped (D-SFC.2), idempotent (a no-op when nothing changed), and atomic (write to a temp file in the same dir + `os.replace` so a crash never leaves a half-written settings.json). If `settings.json` exists but is malformed/unparseable, the composer HALTS the compose step with a clear error and writes nothing (the sync itself already succeeded and stands) — it NEVER overwrites an unparseable file (that would clobber whatever the user has). If `settings.json` is absent, the composer creates a minimal one containing only the composed `hooks` block. Rationale: the only acceptable failure mode on a settings.json the composer can't safely reason about is to do nothing and surface — never a destructive write.

## §7 Out of scope (deferred + when)

1. **Activation against Luke's LIVE workspace** — this build is fixture-tested only. Wiring the composer to run against the live `<workspace>/.claude/settings.json` (i.e. the first real sync that auto-composes the frame-kernel + keep-pace fragments into Luke's actual settings) is the SAME owner-gated step 1a/1b §7-4 + keep-pace RF-6 left open — surfaced for the dispatcher to time when live work is quiescent, NOT part of this seal.
2. **A general settings-key composer (beyond `hooks`)** — this composer composes the `hooks` block only (the fragments declare only `hooks`). Composing `permissions` / `env` / other keys from fragments is a future shape if a component ever ships a non-`hooks` fragment; out of scope now (no fragment ships one).
3. **User-scope `~/.claude/settings.json` composition** — keep_pace's fragment `_comment` targets the USER-scope `~/.claude/settings.json` (not the workspace one). This composer targets the WORKSPACE `<workspace>/.claude/settings.json`. Whether a fragment can declare a user-scope vs workspace-scope target is a follow-up (a `scope:` field on the fragment); v1 composes into the workspace settings only. Named, not silently dropped (RF-4).
4. **Conflict resolution between two loam fragments declaring the same matcher** — v1 composes each fragment's groups additively; if two loam fragments declare identical command groups, dedupe collapses them (D-SFC.1). A richer same-event ordering/priority policy across fragments is a follow-up if a real collision appears.

## §8 Halt triggers (in-flight conditions that abort the build)

1. **Non-clobber cannot be guaranteed structurally** — if, when wiring the composer, the only way to compose into `settings.json` would risk modifying/removing a user entry or a non-`hooks` key (e.g. Claude Code rejects the loam-ownership tag field AND no alternative clean-ownership marker is available, so loam-owned and user-owned entries become indistinguishable) — HALT and surface. Do NOT ship a composer that can clobber user settings; the named alternative: a sidecar `settings.json` fragment-include mechanism if Claude Code supports one, or a more conservative "append-only, never-remove" mode.
2. **Idempotency cannot be guaranteed** — if a re-run cannot detect-and-skip an already-present loam entry (the dedupe key is unstable across runs — e.g. `${LOAM_REPO}` resolves nondeterministically) — HALT and surface; a composer that duplicates entries on every sync is worse than no composer.
3. **Fence breach** — if the natural implementation needs to EDIT a sealed component beyond `workspace-sync` (e.g. modifying `workspace-bootstrap`'s `claude_dir`, or editing the `frame-kernel`/keep_pace fragments themselves, rather than importing/reading them) — HALT; that widens a second sealed fence; surface for a manifest entry rather than silently widening.
4. **`workspace-sync` is the wrong owner** — if, at build time, it turns out the post-merge composer cannot access the workspace root / synced framework tree from `_execute_sync` (it can — `workspace_root` is in scope throughout `_execute_sync`; this is a guard, not an expected trip) — HALT and surface the alternative owner (a standalone `pos-compose-settings` CLI invoked by sync).
5. **Atomic-write infeasible** — if `os.replace` / temp-file-in-same-dir is unavailable for the settings.json target (e.g. a cross-device path) — HALT and surface; never fall back to a non-atomic truncate+write that can leave a half-written settings.json.

## §10 F2 Ruthless Feedback (honest doubts; named design risks)

**RF-1 — the composer deliberately writes OUTSIDE the HC#6 fence; this is a real widening of pos-sync's write surface, named not silent.** *Disagreement:* a reader of the D.3 `cli.py` docstring ("files outside `framework/` are structurally unreachable") would assume pos-sync never writes outside `framework/`; this composer DOES (it writes `<workspace>/.claude/settings.json` at the workspace root). *Evidence:* `cli.py` module docstring HC#6 + `workspace_paths.py:113` (`.claude/` at workspace root, outside both `framework/` and the workspace-state subdir) + the grep showing zero settings.json writes in workspace-sync today. *Alternative / resolution:* HC#6's promise is specifically about GIT operations (`-C <workspace>/framework`) — the merge still happens only in `framework/`; the composer is a NON-git post-merge Python write. The widening is real but bounded: the composer's TOTAL write surface is exactly `<workspace>/.claude/settings.json`, and within it exactly the loam-owned `hooks` entries (D-SFC.2). The plan names this widening (§1, §3-feasibility, here) rather than letting it pass as an unremarked HC#6 violation, and sizes the safety envelope (additive + tag-scoped + idempotent + dry-run + atomic) to the blast radius. If the dispatcher judges the HC#6 reach itself unacceptable, the named alternative is a STANDALONE `pos-compose-settings` CLI that sync merely INVOKES (same code, different fence story — the composer's own component) — surfaced for the ruling, with the EXTEND-workspace-sync shape as the recommendation (the composer's input is a sync-lifecycle fact; coupling it to sync is the natural shape).

**RF-2 — the loam-ownership tag depends on Claude Code tolerating an unknown field on a matcher-group; if it doesn't, the clean-ownership boundary needs a fallback marker.** *Disagreement:* D-SFC.2's non-clobber guarantee rests on every loam entry being unambiguously identifiable; the cleanest mechanism (a `_loam` metadata field on the group) assumes Claude Code ignores unknown keys in `settings.json` hook groups. *Evidence:* the live `settings.json` groups carry only `matcher` + `hooks`; whether an extra sibling key is tolerated is not verified at plan time (it's a live-schema question). *Alternative:* the AC.SFC.2 + §8-halt-trigger-#1 carry this as a build-time check — the builder verifies the tag field is tolerated (a real `claude` run with the tagged settings.json doesn't error); if NOT, the fallback marker is the command-path prefix (every loam command points under `<framework_root>/...` in the synced tree — a structural, schema-safe ownership signal) OR a sidecar manifest (`<workspace>/.claude/.loam-composed.json`) recording which groups loam owns. The plan pins the OUTCOME (clean ownership boundary) and names the fallbacks, rather than betting the safety guarantee on one unverified schema assumption.

**RF-3 — "automatic on sync" is the right default ONLY because non-clobber holds; if RF-2's tag fallback is weaker, the automatic default may warrant a flag.** *Disagreement:* D-SFC.4 recommends automatic-on-sync, justified by the non-clobber guarantee; if the ownership boundary degrades to a less-certain marker (RF-2 fallback), automatic-everywhere becomes slightly riskier. *Evidence:* the blast radius is every workspace's settings.json; the dispatch explicitly recommends automatic given non-clobber. *Alternative:* automatic-on-sync ships as the default WITH the surfaced summary (the operator always sees what changed) AND the `--no-compose` opt-out AND the `--dry-run-compose` preview — so even under the weakest acceptable ownership marker, the action is visible + reversible (re-running with the fragment removed un-composes it; the user's own entries were never in the write set). The recommendation stands (automatic + visible + opt-out), not (gated-behind-a-flag-by-default).

**RF-4 — workspace-scope vs user-scope settings.json: keep_pace's fragment actually targets `~/.claude/`, this composer targets `<workspace>/.claude/`.** *Disagreement:* the keep_pace fragment `_comment` says "activates … in the user-scope `~/.claude/settings.json`"; the frame-kernel fragment targets a workspace `.claude/settings.json`. A single composer that always targets the WORKSPACE settings would mis-place keep_pace's hooks if keep_pace genuinely needs user-scope. *Evidence:* the two fragments' `_comment` fields name different targets (frame-kernel: a workspace `.claude/settings.json`; keep_pace: `~/.claude/settings.json`). *Alternative:* v1 composes into the WORKSPACE settings only (§7-3) — correct for frame-kernel + the common case; the user-scope-vs-workspace-scope target is surfaced as a follow-up (a `scope:` field on the fragment the composer would honour). The plan does NOT silently compose keep_pace into the wrong scope: AC.SFC.* are written against the workspace-settings target + the frame-kernel fragment (the outcome-altitude probe uses frame-kernel precisely because its target is unambiguously the workspace settings); keep_pace's correct-scope composition rides the §7-3 follow-up. Named, not glossed.

**RF-5 — the composer is the FIRST consumer of `settings.fragment.json` as a discoverable surface; nothing validates the fragments today.** *Disagreement:* discovery-by-glob trusts that every `settings.fragment.json` under `framework/*/hooks/**` is a well-formed, safe-to-compose fragment; there is no fragment schema validator. *Evidence:* grep shows nothing globs `settings.fragment.json` today — the composer is the first reader; the fragments carry a `_comment` field + a `hooks` block but no enforced schema. *Alternative:* the composer validates each discovered fragment before composing (has a `hooks` mapping; each event maps to a list of matcher-groups; each command resolves) and SKIPS-with-a-surfaced-warning a malformed fragment rather than composing garbage or aborting the whole sync — a malformed component fragment degrades to "that one fragment not composed + a warning," never a destructive write or a sync abort. This is the fragment-side mirror of D-SFC.5's settings-side safety.
