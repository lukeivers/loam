## §1 Summary / TL;DR

**What ships:** an **IN-SESSION once-per-hour self-wake** — while the interactive session is alive, a **session-scoped scheduled tick (`CronCreate`)** fires hourly and **re-engages the live session** to: **refresh + read PART 1's census** (to know what is genuinely current/done), read the **approved-autonomous-work queue** (the existing autonomy-queue), **continue the next approved-autonomous item** *inside the live session* (full context, visible in Telegram, supervised), **report** the outcome to Telegram (each tick reports what it did OR that it correctly no-op'd), and is **bounded + killable** (one documented `CronDelete` off-switch). It closes the autonomy-continuation hook's gap: that hook fires only on an idle turn-END, so when the agent winds down mid-run, queued work silently stalls — the hourly tick is the periodic heartbeat that re-engages the live session on a clock.

**The failure mode this fixes (the thing Luke named):** long autonomous runs wind down and work silently stalls because the only continuation mechanism (the pos3 Stop-hook) fires only on an idle turn-end — there is no periodic heartbeat that re-engages the session on its own. This is that heartbeat — and it does it **inside the live session**, the safest possible place: full context, real-time Telegram visibility, supervised, trivially killable.

**What does NOT ship now (the owner decision):** the persistent launchd "re-launch the session with `claude --resume`" layer is **DEFERRED** (§7.D). Luke is uncomfortable with a detached self-relaunch out of his control. It is **demoted, not deleted** — §7.D records it as the deferred future-layer with Luke's load-bearing design constraint: **if/when ever built, it MUST check for a live session FIRST and DEFER to it — acting only when there genuinely is no live session** — so it never fights the in-session loop or double-runs. That check-live-session-first / defer-to-it guard is what makes the persistent layer not-hollow; it is the spec for the deferred layer, out of scope today.

**AC families (revised to the in-session shape):**
- `AC.TICK.*` — the in-session tick: a session-scoped `CronCreate` tick fires once per hour, re-engages the LIVE session (restored on `--resume` if the session resumes), is registered/listed/removed through the component's own arming helper + off-switch (not a hand-rolled cron string).
- `AC.RESUME.*` — the continue behavior: the fired tick refreshes the census, reads the approved-autonomous queue, picks the next eligible item, continues it *in the live session*, and reports; if nothing is eligible it correctly no-ops and reports the no-op (each tick reports), never fabricates work.
- `AC.SCOPE.*` — **scope safety (capability-gate)**: ONLY items inside Luke's standing autonomy grant (persona-eligible AND explicitly autonomous-OK) are continued; anything owner-class / public-action / money-spending / irreversible is HALTED-and-surfaced, never acted on.
- `AC.BOUND.*` — **runaway + cost (capability-gate)**: a per-tick work cap, idempotency (an item isn't continued twice), and an overall cost ceiling (the real interactive `/api/oauth/usage` window + the #82 daily-ration cap) — the tick never burns unbounded tokens; on hitting a cap it stops + surfaces.
- `AC.KILL.*` — **off-switch (capability-gate)**: one documented command (`CronDelete` + the tick task id) disables the tick; after disable, no further ticks fire.
- `AC.AUTORESTART.LIVE.*` — **outcome-altitude**: a REAL test fire — the scheduled tick wakes the live session, it reads the census + the approved queue, continues the next eligible item OR correctly no-ops/surfaces if none/owner-class, reports to Telegram, halts on an owner-class item, and the off-switch verifiably stops further ticks. **No launchd, no detached spawn.**

## §6 Acceptance criteria (outcome-shape; method-in-AC test passed on each)

**AC.TICK.1** — A session-scoped scheduled tick, registered through the component's own arming helper (not a hand-rolled cron string), fires once per hour and re-engages the LIVE interactive session; if the session resumes via `--resume`, an un-expired tick is restored. *(Outcome: a periodic in-session heartbeat exists + is component-armed; method — the `CronCreate` cron expression — is the builder's call.)*

**AC.TICK.2** — The tick is registered, listed, and removed through the component's own entry points (arm → list → off-switch), each independently exercisable. *(Outcome: lifecycle-managed in-session tick; method is the builder's call.)*

**AC.RESUME.1** — On a fire, the tick refreshes PART 1's census (drives the on-demand capture pass), reads the approved-autonomous queue, and picks the next item that is BOTH persona-eligible AND autonomous-OK-flagged, continues it IN the live session, and reports the outcome to Telegram. *(Outcome: the fire continues genuinely-approved current work in the supervised live session; method is the builder's call.)*

**AC.RESUME.2** — When NO item is eligible (queue empty, all items owner-class, all blocked, or none autonomous-OK), the tick correctly no-ops, fabricates no work, AND reports the no-op to Telegram (each tick reports — what it did OR that it correctly no-op'd). *(Outcome: correct no-op + a visible no-op report; method is the builder's call.)*

**AC.SCOPE.1 (capability-gate)** — An item that is owner-class / public-action / money-spending / irreversible (or simply not autonomous-OK-flagged) is NEVER auto-continued: it stays queued and, if it's the only thing present, the tick halts-and-surfaces rather than acting. *(Outcome: conservative scope — only doubly-approved work acts, everything else is surfaced not acted; method is the builder's call.)*

**AC.SCOPE.2 (capability-gate)** — The tick can NEVER self-authorize an item: it cannot set autonomous-OK on an item; that flag is set only by Luke or the persona-with-recorded-rationale, never by the self-waking tick. *(Outcome: no self-granted scope; method is the builder's call.)*

**AC.BOUND.1 (capability-gate)** — The tick is bounded per fire (at most the configured items-per-tick / token-per-tick cap) and overall (the daily-ration cap read from the REAL interactive `/api/oauth/usage` window); on hitting any bound it stops continuing and surfaces a cap-reached report, never burning unbounded tokens. *(Outcome: cost-bounded against real usage; method is the builder's call.)*

**AC.BOUND.2 (capability-gate)** — An item is continued at most once per its lifecycle: a continued item is moved to in-flight/completed before the next fire, and a re-fire (or the in-session Stop-hook) does NOT re-continue the same item (idempotent, dedup against in-flight). *(Outcome: no double-acting across the tick + the Stop-hook; method is the builder's call.)*

**AC.KILL.1 (capability-gate)** — One documented command disables the tick (the `CronDelete` + task-id pattern); after disable, the tick does not fire again. The off-switch is documented in the component + in the bookkeeping surface. *(Outcome: a one-command, documented off-switch; method is the builder's call.)*

**AC.AUTORESTART.LIVE.1 (OUTCOME-ALTITUDE, `outcome-altitude:true`)** — A REAL test fire of the production on-wake runbook, end-to-end: the scheduled tick wakes the live session, it refreshes + reads the census, reads the approved queue, and EITHER continues the next approved-autonomous item IN the live session (continues it, reports to Telegram, moves it to in-flight) OR correctly no-ops/surfaces if none is eligible / the only item is owner-class (and reports the no-op) — AND on an owner-class item it HALTS-and-surfaces rather than acting — AND the off-switch verifiably stops further ticks (`CronDelete`, then no further fire). **No launchd, no detached spawn; the real tick, the real census read, the real queue, the real in-session Telegram report.** *(This is the literal "a real test-fire wakes the live session, reads the census + queue, continues OR correctly no-ops/surfaces, reports to Telegram, halts on owner-class, and the off-switch stops further ticks" the objective names. Method is the builder's call.)*

## §10 F2 Ruthless Feedback (honest doubts + named design risks)

1. **★ The one real loss of in-session-only: it stops when the session ends.** *Disagreement / honest naming:* the in-session tick is **session-scoped** — `CronCreate` is cleared on a new conversation and restored only on `--resume` if un-expired (verified: `claude-feature-awareness` SKILL §6, "Needs open session: Yes"). **If Luke closes the session, the heartbeat is gone until he resumes.** It does NOT solve "work continues after the session ends" — only "work continues while the session is alive but the agent has drifted off mid-run." *Evidence:* the SKILL's scheduling-comparison table — CronCreate "Needs open session: Yes; Persistent across restarts: Only via `--resume`." *The alternative / the future answer:* the DEFERRED launchd layer (§7.D) with Luke's check-live-session-first design IS the answer to this loss — it would continue work across session boundaries, deferring to any live session. *Why in-session-only is still the right call TODAY:* it solves the named failure mode (mid-run stall while alive), it is in Luke's comfort + control (he is uncomfortable with detached relaunch — D8), and it is materially lower-risk (no bot-slot theft). The loss is real and named; the future answer is recorded, not lost.

2. **★ Continuing work it shouldn't (scope leak).** *Disagreement:* a self-waking tick that continues work on a clock — even in the live session — must not continue an item that was only ever safe under a fresh human prompt. *Evidence:* the pos3 hook's `_pick_next_queued` filters only owner-class + blocked; it assumes a live human-prompted turn. *Bound:* the doubly-gated signal (D2 — persona-eligible AND explicit autonomous-OK), the tick can never self-authorize (AC.SCOPE.2), owner-class is halted-and-surfaced (AC.SCOPE.1). Scope safety is independent of the in-session decision — it is NOT relaxed by the lower-risk mechanism.

3. **★ Runaway token spend.** *Disagreement:* a self-waking hourly tick that continues work is still a spend risk — a never-emptying queue could burn the interactive cap. *Evidence:* an unbounded in-session loop is the same hazard as an unbounded detached one, just on the interactive bucket. *Bound:* the daily-ration cap (#82, default 15%/day) read from the REAL interactive `/api/oauth/usage` window (AC.BOUND.1) + one-continue-per-tick + a max-items/day; on any cap, stop + surface. The cost ceiling is the D3 owner call — Luke sets the numbers before he arms it.

4. **The proven bot-slot-theft risk is ELIMINATED from the build scope (the prior #1 risk, now gone).** *Honest reframe:* the prior launchd version's highest risk was a detached `claude -p` SIGTERM-stealing the single Telegram bot slot every hour (`feedback_spawned_claude_must_isolate_telegram_plugin`). **The in-session mechanism has no detached spawn — the tick re-engages the LIVE session, which already owns the bot slot. There is nothing to steal it.** *Evidence:* the owner decision removes the detached relaunch from scope; the in-session reply uses the live MCP. *Consequence:* the `AC.ISO.*` family + D4 are RETIRED (no isolation to test because there is no spawn to isolate). The risk is recorded as a precondition of the DEFERRED §7.D layer (which WOULD spawn headless and WOULD need isolation), not of this build.

5. **Double-acting across the tick + the Stop-hook.** *Disagreement:* the tick and the in-session Stop-hook share the same queue; both could continue the same item. *Evidence:* the `feedback_serialize_amendment_builds` race hazard, here within one session. *Bound:* idempotent continue (AC.BOUND.2 — move to in-flight before the next fire) + the dedup-on-in-flight (D6 — the tick continues the NEXT eligible item or no-ops if one is already in-flight). Same driver, two triggers; never two continues of one item.

6. **★ Feasibility-honesty: is this buildable to a verified test-fire TODAY?** *The honest read:* **YES — this is lighter than the launchd version and realistically buildable to a verified test-fire today.** It removes the three heaviest prior pieces (the plist generator, the detached-spawn runner, the isolation wiring) and leans on the shipped `CronCreate` + the existing autonomy-queue pick-logic + PART 1's census (sealed-local on `build/self-maintaining-work-loop`). The remaining work is the on-wake runbook (refresh census → read queue → doubly-gated pick → continue-in-session → report), the arming helper, the off-switch, and the test-fire. *Estimate band (AI-time, midpoint):* a single new-but-small component composing on a shipped primitive ≈ 20–40 wall-clock min of agent work, plus the owner rulings on D2 + D3 (set before live-arming, NOT before the test-fire). *The one dependency:* PART 1's census must be readable (it is — sealed-local); if it somehow isn't, §8 halt #3 ships the safety scaffold today with the census-read behind a fail-soft seam. *I will NOT claim the LIVE recurring tick is running today* — that is owner-gated (D7); the build delivers a verified test-fire + the arming helper, and Luke arms it live on his explicit "arm it."

7. **Scope-confidence (F4) note.** The in-session `CronCreate` + the autonomy-queue pick-logic + the in-session Telegram report are HIGH-confidence (the primitive is shipped + documented; the pick-logic is ported from the proven hook; the live MCP report is the normal path).
