# FUTURE_IDEAS_DRAFT.md — no-overhead idea capture

This is a draft surface for *every* improvement idea about pos-v2 — Luke's or the assistant's — captured at point-of-occurrence with no overhead. Sibling to `FUTURE_IDEAS.md` but distinct in lifecycle:

- `FUTURE_IDEAS.md` is **curated**: each idea has a designated number, a rationale section, and a relationship to other ideas.
- `FUTURE_IDEAS_DRAFT.md` is **no-overhead capture**: append a brief bullet with rationale (~3–5 lines) the moment an idea surfaces. No numbering, no curation, no ordering.

**Lifecycle.** During the initial phase of pos-v2 development, entries accumulate. After the initial phase concludes, a daily rigor reviews the draft:

- Incidentally-actioned items get removed (the work happened, the idea served its purpose).
- No-longer-relevant items get pruned.
- Graduate-worthy items get promoted to `FUTURE_IDEAS.md` with full curation.
- Others get dropped or restated.

**Convention.** Agents (background or main-session) **surface to chat** — they do not write to this file directly. The parent (or owner) appends. This avoids file-write races when multiple agents run in parallel, and keeps the parent in the loop on every captured idea.

**Why this exists.** Asymmetric findings, deferred decisions, anti-pattern observations, and feature ideas are valuable signals. Without a destination, they drift away in chat or get lost in memory churn. `FUTURE_IDEAS.md` is too weighty for impromptu capture; this file is the lower-friction destination.

- **Vertical swarming — context-domain decomposition as a first-class swarm shape.** Captured 2026-05-04 by main session per Luke's directive ("this sounds a lot like swarming concept, but at a different layer. Please focus on this idea of relating it to swarming"). The connection: current F3 swarming pattern is **horizontal** — decompose ONE task into tighter sub-tasks with tighter ACs, run them, aggregate, done. The PM-persona shape is the same operation **vertically** — decompose ONE ongoing CONTEXT into tighter sub-contexts (PMs hold project-domain state; specialist helpers may hold task-domain state if persistent state accumulates). Sub-contexts are not transient like sub-tasks; they live as long as the domain does. **Stopping criteria mirror:** horizontal stops when split adds only coordination overhead; vertical stops when the parent can hold the sub-context's state without losing fidelity. **Triggers differ:** horizontal triggers on "this task is decomposable into tighter sub-tasks"; vertical triggers on "this thing needs ongoing attention bigger than the parent should reasonably hold." **Two derived rules:** (1) Split a context-domain off when persistent attention required exceeds what the parent should reasonably allocate — don't split for one-shot work. (2) Default to transient; promote to persistent only when accumulated state would be worth keeping warm (project-specific builder learning build quirks = candidate; one-off researcher = stays transient). **Layered example for loam:** primary persona's context = harness + Claude + Luke's needs across all projects → when ONE project develops enough ongoing state, split off a per-project PM → within a PM, helpers default transient but may go persistent if a builder/tester etc. accumulates project-specific patterns. **Composes with:** F3 swarming-recursive-decomposition (this extends it with a persistence axis); per-project-PM FIDRAFT entry below (this is the principle that justifies that shape); v0.2 swarm-runtime planned work (V2.C currently conceived as task-decomposition only — adding persistent-context capability extends the runtime cleanly; vertical swarming becomes first-class, not a special case). **Implication for swarm-runtime spec:** when V2.C is authored, the PlannerWorkerSwarm cycle pattern needs an analog for persistent-context entities — call it `ContextManager` or similar — with `is_persistent: bool` + `context_domain: <scope>` fields on every spawned entity. **Status:** captured as design-principle for the next planning session + the v0.2 swarm-runtime spec.
